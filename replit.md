# Valo Pay 1

Observation-first collections operations for Nigerian lenders. The current application is an isolated, persistent **synthetic sandbox**, not a live-ready Stage 1 release.

## Run & Operate

- Use the managed `artifacts/api-server: API Server` and `artifacts/valo-pay-1: web` workflows; their ports are injected.
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/valo-pay-1-api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec; `pnpm run check:contract` regenerates and fails if the committed files differ
- `pnpm --filter @workspace/valo-pay-1-db run push` — push DB schema changes (dev only)
- The schema source includes the ordinary foreign keys, unique indexes and money/floor checks. No custom role, policy, function or trigger setup is required. Do not run DDL at app startup, in publishing build commands or against production automatically.
- `node scripts/smoke-valo-pay-1.mjs` — API smoke checks against a fresh synthetic workspace on the development domain; no real lender data.
- `node scripts/check-db-boundary.mjs` — disallow raw database access outside the explicit repository internals, export job store, runtime isolation and subordinate financial projection; block external imports of private repository capabilities. Negative fixtures run in both normal test runners.
- `VALO_PAY_1_RUN_INTEGRATION=1 pnpm run test:integration` — the repository and scheduled-close suites against `DATABASE_URL`, which must be a disposable development database with the schema pushed, under any name; it runs every suite and names the failures at the end. The three migration rehearsals need a loopback PostgreSQL whose login can create databases and skip, saying why, elsewhere (such as Replit's managed database); the pull-request workflow runs them all against its own PostgreSQL service container.
- `node scripts/security-valo-pay-1.mjs` — negative and concurrent API checks using fresh synthetic development workspaces.
- The API process runs the scheduled daily close (REC-01, default 07:00 WAT per lender) from `artifacts/api-server/src/lib/close-scheduler.ts`; set `VALO_PAY_1_CLOSE_SCHEDULER=off` (any case; any value but `on`, `off` or `external` stops the process at startup) to run a process without it. The close scheduler and the export worker both run inside the API process, on its background worker thread (`artifacts/api-server/src/background.ts`, its own pool of three connections, started again after a crash), and the deployment is Replit Autoscale, which scales to zero: no close or export runs until a request starts an instance, and the per-address limits count per instance. Closes run on time on a Reserved VM, or on Autoscale with `VALO_PAY_1_CLOSE_SCHEDULER=external` (no scheduled close in the process, which reads the lenders still owed a close every minute for `/api/healthz`, so a close the job misses shows as overdue there and still raises `close_missed`) and a Scheduled Deployment running the one-shot close pass (`node --enable-source-maps artifacts/api-server/dist/close-pass.mjs`, exit 0 done, 2 a close failed, a lender's close is still failing or overdue, or its ten-minute budget ran out with lenders still due, never for a public anonymous sandbox's close alone, 1 could not run or was stopped); the owner chooses (`docs/deployment.md`). A stopped worker returns its unfinished exports to the queue.
- The deployment (`artifacts/api-server/.replit-artifact/artifact.toml`) gates a release on `/api/readyz`, turns the expired-sandbox cleanup on (`VALO_PAY_1_EXPIRED_WORKSPACE_CLEANUP=on`) and sets `CLERK_TELEMETRY_DISABLED=1`. Apply migrations by hand before publishing: `docs/database-migrations.md`. The API checks its settings at startup and stops with one `config.invalid` line on a bad value.
- Pilot administrators: `scripts/provision-pilot.ts` provisions the first, adds another (`--add-administrator`) and renews one (`--renew`), each repeatable (`docs/pilot-workflow-release.md`).
- Required integrations: PostgreSQL, managed Clerk and private App Storage. Never display their environment secret values.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod 3 generated API validators and Drizzle insert schemas
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (ESM bundle), Vite React console

## Where things live

- Source requirements: the docs/source folder of the Replit workspace, deliberately excluded from the public repository (business-plan attachments); the v2.1 Gate Change Note supersedes old Business Plan gate wording.
- API contract: `lib/api-spec/openapi.json` (generated by `node scripts/create-valo-pay-1-spec.cjs`); generated hooks and validators must be regenerated together.
- Domain rules: `artifacts/api-server/src/domain/`. Record data is typed per kind from `lib/valo-pay-1-schema/src/records.ts` (`TypedRecord<K>` through `recordsOf`, `findRecord`, `makeRecord`); declare a field there before using it.
- Final-state and provider-evidence guards: `artifacts/api-server/src/domain/final-state-integrity.ts` and `artifacts/api-server/src/domain/provider-event-integrity.ts`. These receive records, never database clients; the scoped repository remains responsible for locking and saving.
- Reconciliation coordinator: `artifacts/api-server/src/domain/reconciliation.ts`. Its `reconciliation-*` modules separate evidence ingestion, matching and its pass-local index, settlement identity/totals, payments/allocations, instalment repair, reversal holds, retry decisions and exception lifecycle. The coordinator keeps the original ordered synchronous indexed pass and explicit public exports; shared record values live in `reconciliation-values.ts`.
- Tenant transaction, audit chain, imports and exports: `artifacts/api-server/src/lib/valo-pay-1-*`.
- Repository facade: `artifacts/api-server/src/lib/valo-pay-1-store.ts`. Private `lib/repository/core.ts` owns transactions, locks and the session map; typed factories separate team access, recovery journal, read models, retention, export cleanup, payload rewrap and readiness. Import only the facade from application code.
- Ordinary database constraints and tables: `lib/db/src/schema/valo-pay-1.ts`.
- Security boundary and publishing limitations: `docs/DATABASE_SECURITY.md`.
- Console: `artifacts/valo-pay-1/src/`.
- Console submission lifecycle: `artifacts/valo-pay-1/src/lib/submission-attempt.ts`; pure outcome classification: `artifacts/valo-pay-1/src/lib/submission-outcomes.ts`. The generated/pilot and connected adapters supply explicit completion policies and keep their own transport and receipt checks.
- Console workflow components: `artifacts/valo-pay-1/src/features/cash-desk`, `features/credit-desk` and `features/imports`. Pages own navigation and workflow state; the import editor keeps hydration, draft, cancellation and recovery sequencing together. Cash/Credit models derive from the shared connected schema; import models distinguish list summaries from full detail and write receipts. `useTypedPilotMutation` validates workflow-specific receipt fields after the existing route and lender checks.
- Readiness and delivery limitations: `docs/BUILD_STATUS.md`.

## Architecture decisions

- **Observation first.** The governing amendment permits building before legal sign-off, but prohibits live instruction. Synthetic evidence must never satisfy a real gate.
- **Do not process real customer data.** Pre-data requires NDPA/DPA, security foundations and approved hosting basis; none is inferred from a user checking a box.
- **Accepted implementation direction.** Technical Requirements v2.0 retained the TypeScript modular monolith and explicitly ruled out an unrelated FastAPI rewrite; v2.1 preserves that direction. This workspace uses TypeScript/Express/Drizzle/PostgreSQL. The accepted stack does not establish production control, hosting or performance acceptance; see the current planning versions and boundaries in `docs/document-register.md`.
- **Demo personas are not production RBAC grants.** Each isolated sandbox may switch simulated actors to exercise separation of duties; real staff provisioning and mandatory MFA remain production blockers.
- **No production adapter guessed.** Aggregator selection follows written partner access. No merchant-secret entry form, funds account, wallet, routing-at-failure or recovery-fee implementation.
- **Application identity is `valo-pay-1`; visible brand is “Valo Pay 1”.** The console is `artifacts/valo-pay-1`. Owned settings use `VALO_PAY_1_`, browser state uses `valo-pay-1:<environment>:`, and the sandbox cookie is `__Host-valo-pay-1_<environment>_sandbox` on HTTPS (without `__Host-` on local HTTP). The only legacy-cookie transition is the reviewed, deadline-bound opt-in at the exact retained generation-1 origin; it retains the old secure host-only token/principal and expires its old name. Old plain cookies are never trusted. Hosted builds require explicit auth/origin configuration and backend resource bindings before they start; see `docs/product-identity/cutover-recovery.md`. Existing SQL names, public wire values and cryptographic inputs remain compatibility contracts, not active application naming defaults.
- **Application-enforced isolation.** The scoped repository, explicit ownership predicates and locked transactions enforce tenant isolation and protected-record rules. This is not independent database-level isolation or immutability: privileged direct SQL or an unscoped code path could bypass those checks. The opt-in restricted runtime (`VALO_PAY_1_RUNTIME_ISOLATION=staging`, migrations `lib/db/migrations/005_runtime_isolation.sql` and `lib/db/migrations/006_runtime_isolation_scope.sql`) adds forced row security for a separately commissioned staging schema; it is off by default. Real lender data remains prohibited.

## Product

Two synthetic lenders; customer positions and timelines; mandate tracking; schedule and external-attempt imports; policy review and read-only backtesting; canonical reconciliation and allocation approvals; exception queues; audit verification; private PDF/CSV/JSON exports; independent readiness gates and synthetic measurement.

## Gotchas

- Amounts are safe integer kobo. Refuse due items below 500,000; 500,000–999,999 requires a recorded merchant Admin override. This floor does not reject inbound partial payments.
- All workspace/merchant operations, imports, exports and idempotency use the scoped repository's explicit `valo-pay-1-store.ts` facade. `scripts/check-db-boundary.mjs` allows database operations only in reviewed repository internals, the export job store, runtime isolation and the subordinate financial projection. Routes and domain modules must never import repository internals or receive raw clients or unrestricted query functions. In staff mode (`VALO_PAY_1_STAFF_ACCESS=staging`) every staff request passes the access and MFA check in `docs/pilot-security.md`. Keep workspace, principal and merchant locking across validation, mutation and audit append.
- Every transaction checks out through `checkOut` and begins with `beginStatement` (`artifacts/api-server/src/lib/database-limits.ts`), so it carries statement, lock and idle limits. Never use a bare BEGIN or an unlistened pool client: an unheard client error ends the process.
- `loadState` leaves an import batch's protected `csv` and `check` sealed. A route that shows or uses raw source rows calls `revealImportPayloads` first (in a write, before the domain changes the batch); the domain refuses sealed rows with a 500 (`assertSourceOpened`).
- Use one audit-hash canonicalisation implementation. Independent hash formats cannot share a chain.
- Orval's post-generation barrel normalisation is intentional; generated request parameter types and validators otherwise collide.
- App Storage provides private persistence, but retention lock, six-year policy and crypto-shredding are not certified.
