# Pilot operations controls

This release extends the synthetic pilot across imports, source checks, personal work, independent close review, staff access and retention. It does not enable real customer data, payment instructions or production access. External commissioning requires a separate identity application, restricted database credentials, private storage and managed key access. No Paystack account or test key is available, so no external Paystack connection has been verified.

## Journey and Finance evidence

Journey steps distinguish not started, in progress, awaiting review, blocked and completed work. Completion requires saved imports, reconciled evidence, resolved cases, a current independent approval and an export tied to that approval. A customer, allocation, close or unrelated export alone does not establish completion.

New manual and scheduled closes record a fingerprint of financial inputs. The preparer names an active Finance reviewer with access to the lender, explains discrepancies and records acceptance of unresolved items. A different authenticated person must decide the review; switching demo personas cannot provide independence. Concurrent decisions and stale versions are refused. Corrections, or a newer close of the same business date, make earlier approvals historical without changing their evidence; a later date's close does not, so each missed date's catch-up close can be reviewed on its own while the records it saw are unchanged.

Reviewed-close exports carry the immutable review ID and snapshot digest. A new export needs the review to be current, checked against its whole stored close: a load otherwise keeps a close more than seven days older than the newest as its summary, so the export request loads that one close whole, as the review's decision does. Generation uses the saved snapshot and explanations, rather than recalculated current figures. A ready checksum must reference the current approved review before the journey marks evidence exported.

A request the service refuses outright (validation, permission, a missing record, a stale version: a 4xx the same request would receive again) closes its journal entry with the reason instead of leaving it pending. Only a request whose outcome is unknown (a lost response, a service failure, a rate limit) stays pending, and only pending entries count towards the limit of 100 per person and lender, so a run of refused submissions can never lock a person out. A closed entry's key cannot run again; a corrected submission carries a new key. Its answer says `operation: "cancelled"`, as does any later request with the same key, so the console can release a request it was holding as unconfirmed. A cancelled entry never completes: an earlier attempt with the same key that is still running is refused at completion, saves nothing and is answered with the same marker. A pending entry whose key already has a stored receipt, from a write saved before the journal existed, is not closed by a refusal and its answer is not marked: that request was saved, which is also why Operations will not cancel it.

Source rows are screened for raw bank details where the batch is saved, whatever route or key delivered them; the recovery middleware's screen is a second line, not the only one.

## Sources and personal work

Source profiles reuse mappings, amount units and row identity columns. Expected delivery intervals and grace periods expose missed feeds; later uploads do not erase earlier missed intervals. Optional row and amount totals are checked before commit. An amount total is in naira and is compared with a batch's naira rows only: each source and newly imported total sums the naira rows and lists money in another currency beside it, never in it, and a batch with rows in another currency needs review while its profile expects an amount. A batch committed by an earlier build keeps the totals it was committed with, which may add rows in other currencies. Corrections retain source identities and revision history.

Each WAT business date now has an append-only declaration of expected source files and their original row and amount totals. Imports carry their business date separately from arrival time. One file cannot satisfy two business dates. An active profile counts as expected for a business date only from its first expected delivery, so a profile created for a feed that starts next week raises no issue for this week's closes. Missing declarations, missing or uncommitted files, mismatched totals, undeclared files and omitted active feeds stay visible in the close. A declared total is in naira and is compared with the file's naira rows, so a file with rows in another currency stays incomplete and says which money no declared total covers. A file whose batch was committed by an earlier build is compared with the total it was committed with, which may add rows in other currencies. A declaration of no files also requires independent Finance acceptance. The preparer explains every issue; the named Finance reviewer must accept each remaining source issue with a reason and supporting evidence, or return the review. Later source arrivals or declaration revisions require a new close; historical approvals retain their original evidence.

A scheduled close checks the source files of the business date it closes: the WAT day before its scheduled time, so the 07:00 close of 29 June checks 28 June, whatever the configured time. When scheduled closes were missed, for example while the service was down, each missed business date gets its own catch-up close, oldest first, with its own source check and Finance review; the scheduler runs one catch-up close per lender per pass and the `close_missed` alert names the dates still owed. Reports can select an earlier source business date for a manual close; future dates are refused. Without one, a manual close run while a scheduled close is missed takes the place of the oldest and checks its date; otherwise it checks the WAT date it runs on. A selected date other than the owed one leaves the missed closes owed. This selects the source files to check and does not backdate the financial snapshot or its reporting interval. The close continues to record when it ran, and its name gives the business date it closed when that differs from the run date.

Committed import corrections use a separate comparison and approval workflow. Supported changes are customer display name or masked phone, and the amount or due date of an unpaid scheduled instalment with no collection or payment dependencies. The comparison lists affected records, and the closes and close reviews recorded up to the comparison time, before submission. A close recorded afterwards (the next scheduled close) carries the same uncorrected value but does not change what approval does, so it does not invalidate an open proposal; a new payment or collection against the instalment does. A proposal checks each of those closes and close reviews as the comparison lists it (its name, reference, status and version): a load keeps a close more than seven days older than the newest close as its summary, and later daily closes that move that cutoff past an earlier close no longer make an unchanged proposal stale, while a decision or reassignment of an earlier close review still does. A proposal saved before this rule keeps its first check, of every record whole as loaded, so it reads as changed once one of its closes loads as its summary; its reviewer rejects it and a fresh proposal is prepared. The amended record is checked with the proposer's own authority, as their direct edit would be, whoever views or decides the proposal: only an Admin's proposal may set an instalment between ₦5,000 and the lender minimum under its override reason (MAN-07); a proposal recorded before the proposer's role was kept is checked as a writer who is not an Admin. The named independent Finance reviewer approves or rejects the exact proposal; source batches, original row provenance, before/after snapshots and every decision remain unchanged. Changed records or dependencies make a proposal stale. Existing financial evidence must be handled through its investigation, reversal or adjustment workflow, rather than rewritten through import. Pending financial corrections prevent close approval. Switching demo personas cannot supply an independent reviewer.

Saved exports expose their processing stage, last progress and recovery status, judged by the database clock of the request that reads them. A write to a claimed job waits for a lender that another change holds, and brief contention is retried against the existing artifact and lease, without generating another file; a lender that stays busy past the retries of a progress or failure write gets the job handed back to the queue, instead of leaving it running under a five-minute lease with Retry unavailable. Lost leases cannot complete another worker's job. A worker stopped by the host returns its unfinished jobs to the queue instead of failing them. Persistently blocked confirmation preserves a recoverable job and the original object identity; stalled work appears in the operational alerts and the Exports page. Storage transfers and repository waits have bounded cancellation or timeout controls. These controls improve recovery but do not establish a production availability commitment.

My work lists assignments, handovers awaiting acknowledgement, due actions and close reviews. It calls a pending close review current or stale as its decision does, also when its close is more than seven days older than the newest close and is loaded as its summary: the summary must match the review's snapshot. A decided import correction is not compared again, and a read or acknowledgement derives only its own item. Reading a notice and accepting a handover have separate durable receipts. Acknowledgement requires the current assignee, assignment event and record version. It does not resolve the case or change financial status. Supervisors see workload and items overdue by at least 24 hours. Notices are in-app; no email service is configured.

## Paystack boundary

Fixed local scenarios cover signed synthetic payments, duplicates, changed amounts, stale mandate events and tampered signatures. They never contact Paystack. Optional test ingress at `POST /api/v1/providers/paystack/{connectionId}/events` checks each delivery's signature on its raw bytes before the lender is locked or read, and saves normalised evidence in a durable lender inbox; [the Paystack guide](paystack.md#signed-test-ingress) gives its configuration and answers. An operator-provisioned opaque connection resolves to an existing workspace and lender. Browser state, query strings and event fields cannot choose that scope. Live-mode evidence is rejected. Ingress creates no payment, allocation, debit or mandate authority; signed evidence still requires independent verification.

The existing read-only adapter supports future account/transaction verification. Configure `PAYSTACK_TEST_SECRET_KEY` through the host secret manager only after an account exists. External connectivity and Direct Debit availability require separate verification. The [Paystack webhook documentation](https://paystack.com/docs/payments/webhooks/) defines the signature and acknowledgement contract.

## Staff access and encryption

New non-administrator memberships have no lender grants. Administrators assign lenders with a reason and expected membership version. An invitation or membership change that grants Admin, Finance or Compliance reviewer takes effect only when a second administrator approves it, and people who are not administrators see only the colleagues on their own lenders ([separation of duties](pilot-security.md#separation-of-duties-in-a-staff-pilot)). Revocation, role changes and invitation reacceptance clear old grants. Lists, direct links, recovery requests and eligible case/review assignees enforce the same scope. A revocation, role, lender-access or invitation change waits only for the requests already running in the workspace: requests that arrive meanwhile queue behind it, so steady polling cannot hold it off, and they run with the change applied. If the running requests do not finish within the request lock limit (5 s), the change answers 503, nothing changes, and it can be tried again. Under restricted database access a read queued behind a change to its own membership is refused with a 409 and the retry reads the new membership.

`lib/db/migrations/004_staff_lender_access.sql` is additive and applied after 003 like the other required migrations; `docs/database-migrations.md` gives the order, the commands and how to verify each. `lib/db/migrations/005_runtime_isolation.sql` is a separate commissioning migration; it refuses public schemas and unknown pre-existing policies. `lib/db/migrations/006_runtime_isolation_scope.sql` must follow it in the same schema, with its own `valopay.runtime_migration=staging-only` opt-in: it keeps the same rules and policy names but works out the lenders a person may see once per statement instead of calling a helper for every row. With 005 alone, a 13,000-record lender took about ten seconds to load and the export claim reached its five-second timeout; with 006 the same load takes under 100 ms. The application refuses a runtime schema without 006. The runtime login can update a workspace's merchants, records, journal, memberships and invitations within its row scope, never a workspace row: its one column grant on that table exists so it can take the row locks every staff request needs, and a guard trigger refuses any change it attempts, because staff roles come from memberships. The rehearsal checks both. It installs a restricted runtime login and a distinct non-login helper owner, fixed helper search paths and forced row security across ten application tables. In every isolated transaction the application checks its database role (no superuser, `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`, no membership of any role, since the login could take up that role's privileges, and no `CREATE` on the runtime schema) and then compares the isolation set with the reviewed one in `artifacts/api-server/src/lib/runtime-isolation-policy.ts`: each of the 25 policies' command, roles, permissive mode and `USING` and `WITH CHECK` expressions as PostgreSQL writes them, each scope helper's owner, fixed search path, signature and body, the workspace guard trigger's definition and enabled state, and every privilege the login holds on a table or one of its columns in any schema, granted to it or to PUBLIC, against the 40 that migration 005 grants (`reviewedRuntimeGrants`). Any other relation or function in the runtime schema, such as a view or a sequence, is refused as well; outside the runtime schema, relations an extension installs are left to it. The catalogue is read with `pg_catalog` first, so an object in the runtime schema cannot stand in for a built-in. Any difference, such as a policy altered to `USING (true)`, a replaced helper, a disabled guard, `GRANT TRUNCATE`, the `REPLICATION` attribute, membership of `pg_execute_server_program` or a view over the records, refuses the request with a 503 and logs what differs, so the readiness page reports the database as verified for a request only when that request's own check passed. A migration that changes a policy, a helper or the guard updates that file in the same reviewed change. The check runs in every isolated transaction and costs about 6 ms (four round trips; planning its two catalogue reads is about 2.5 ms of it, and reading and rendering the catalogue about 2 ms on PostgreSQL 16), against about 18 ms for a light read request; it stays per transaction because the readiness page reports the database as verified only for a request whose own check passed. The reads are not named statements, which each connection would plan only once: behind a transaction-mode pooler without prepared-statement support, a transaction can run on a server connection where a statement prepared on another does not exist, and every isolated request and background transaction would fail. Caching it behind a catalogue fingerprint was considered and not adopted: the fingerprint would have to cover role attributes and memberships as well as the policies, helpers, guard and table settings, and missing one would verify a request that was never checked. The recorded expressions are PostgreSQL 16's rendering: after a major-version upgrade, run the runtime isolation rehearsal on the new version before enabling staff access. Workers require a provisioned service member and recheck the original export requester's authority.

Managed envelope encryption protects original import CSV and validation previews, operation requests and refusal receipts, and idempotency responses. An operation request is the keyed write as it was sent: its method, path and whole body, fields no route reads included, up to the body limits (2 MB and 10,000 values), because a retry from Operations sends that body through its route again; a repeat with the key is compared with its fingerprint, a digest of it. A completed request's journal entry keeps only a reference to the record it saved (its ID and kind), stored unsealed so Operations can link to the saved result without the key service. Each payload receives a fresh data key and authenticated lender/record/field scope. Managed KMS wraps the data key; the database stores ciphertext and key identifiers. Protected source rows are opened only by the views that show or use them, at most four at a time: a batch's detail, its commit, Sources for batches not yet committed (and for committed batches stored without source quality), the retention screens, and the batch list, which opens the check of a batch saved before check summaries were stored (such a batch has none, and a committed batch never gains one). Overviews, other lists, scheduled closes, Paystack test receipts and saves sent without an idempotency key that do not touch an import batch make no key-service call, so they keep working while it is unavailable; the batch list keeps working too, and shows those older batches without their check counts. Console saves carry an idempotency key, and a keyed save seals its journal and replay records (an import batch save also seals its rows), so it fails closed (503) during an outage. The provider uses [Google Cloud KMS](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/encrypt) with Application Default Credentials. Missing or wrong keys fail closed. Team & access provides a synthetic key-access check and bounded protection of legacy payloads. Financial record fields, operational metadata and audit content are outside this added envelope layer; whole-database encryption and completed security acceptance are not claimed.

Keep old keys available during rotation and restore. Verify the new key, protect new writes, migrate historical envelopes with the operator's re-wrap step ([key rotation](pilot-security.md#key-rotation)), and rehearse restore before retiring old key access. No raw key material is exported. Actual identity/MFA, KMS and restricted-database commissioning must be verified on the configured host; local fixtures do not establish those external facts.

## Retention and disaster recovery

Raw CSV, terminal recovery payload and export-file retention default to disabled. Financial and audit records remain retained. Policies and item holds require reasons and retain history. A policy cannot set a shorter period than the workspace's minimum, and a policy saved before the minimum existed is applied as if it were the minimum. In the anonymous sandbox every category keeps at least 30 days, the time an inactive sandbox is itself kept, so a one-day policy cannot delete sample work the day after it was made. A staff pilot rehearses a regulated lender: original source files and export files are its evidence and keep at least six years (2,192 days, which covers the leap days any six years hold), the evidence period these documents name for private storage (`replit.md`); completed and cancelled request payloads keep at least a year (366 days), one annual audit cycle, since the records they created and the audit trail that names them are kept regardless. The retention view carries the minimums (`minimumDays`). In a staff pilot an administrator other than the one who prepared a preview approves it (403 otherwise), and either may execute it; the sandbox has one person playing every role, so there the console explains the rule without enforcing it (`secondApprover`). Preview lists up to 100 exact eligible source identities/digests and expires after 15 minutes. A completed or cancelled request's digest covers its request's fingerprint (the digest of the request as it was sent, with which a repeat of its key is compared), its key, its outcome and its version, so no retention request reads a request's body: an entry's payload changes only when it settles, which moves its version, and sealing or re-wrapping it changes nothing it holds. A run prepared before that digest holds the earlier one, of the stored request and receipt, and its approval and execution compute it again for the run's own sources, each stored version of an entry once in a process. Approval revalidates current policy, holds and source versions. Execution runs under the lender lock and removes the run's sources one after another until two seconds have passed, starting none after that (`domain/lifecycle-run.ts`), so a request normally holds the lock well inside the five seconds other requests wait for it; each source is checked again just before it is deleted and gets a success, failure or blocked receipt. A blocked source, or a deletion that cannot be confirmed, stops the run with its reason, and the sources after it are not attempted. The console repeats the request until the run completes or stops, showing how many sources are removed, and its Stop ends the run after the current request. It used to delete one source per request, so each needed a click. Resume uses the same saved manifest, sources not yet attempted first, so a blocked or failed source is tried again last. A database error in a request still rolls the whole request back; an export file it had already deleted is then found already absent when the run resumes. Export deletion checks ownership, checksum metadata and object generation; a lost acknowledgement can recover from an already absent object. An export file linked as evidence to a case that is still open, or the reviewed-close export of an approved Finance close review, is kept whatever the policy says: it is never eligible, so it needs no hold, and the retention view says why for each such source (`evidence`, counted in `evidenceTotal`). Resolving or closing the case releases its evidence; an approval is final, so its export stays. A file linked after a preview blocks the approval, and after an approval blocks its deletion. Each retention request reads the policy, the holds, the evidence and the saved receipts once and then checks every source it lists by lookup, so its cost grows with the lender's records plus those sources: with 5,010 terminal journal entries on a 25,000-record lender the view took about 0.5 s, where checking each source against the whole lender again took about 4 s. Request payloads are listed a page at a time: the view reads those its page can hold (as many as the lender has import batches and exports, and 100 more), a preview the oldest 100 and one more for each held request, and an approval or execution its run's own, while the database counts the rest, so with 100,000 retained requests the view answers in under 0.2 s.

Journal redaction retains request keys, fingerprints, actors and terminal status. Matching replay responses become expiry markers that prevent re-execution. Pending requests are never candidates. A completed request's answer is stored once, as the replay copy in `valopay_idempotency` under its journal entry (one person's request on one route, so the same key used on another route or by a colleague never answers it), which is what a retried key or a retry from Operations replays; answers saved by earlier builds stay under the key alone and still replay; the journal entry keeps only a reference to the record it saved, which Operations links to. A daily close answers with its whole record (about 100 KB for a pilot-scale lender), and both tables used to hold it; entries completed before this change keep their whole answer until a retention run removes it. Old answers leave only through these reviewed runs, whose markers answer a retried key with 410 instead of running it again: nothing removes them by age alone, because that would bypass the preview, the approval and the receipts. The replay copies of keyed requests the journal does not record (demo persona switches, kept under a name of their own, and writes saved before the journal existed) are small and are kept. Raw-file removal preserves committed records, source identity and revision history. File expiry prevents downloading or retrying the expired export job; a new export is a separate request.

The recovery rehearsal restores all eleven application/service database tables, generated private-file bytes/metadata and reviewed key/access configuration. It verifies checksums, missing files, wrong keys, lender-bound decryption, audit chains, replay state and orphan export cleanup records with their retry/backoff and lease state. The cleanup queue remains outside restricted tenant runtime schemas. Timings and snapshot age are recorded, including an intentional post-snapshot lost write. These measurements do not establish a production recovery commitment. See [operational rehearsals](operational-rehearsals.md).

## Verification

`lib/api-spec/openapi.json` describes every route the API mounts, including the Paystack test ingress `app.ts` mounts outside `routes/index.ts`; `scripts/check-docs.mjs` follows every router `app.ts` mounts under `/api` and fails when one of its routes is missing from the contract or when it cannot follow a router `app.ts` imports from `routes/`, and the request and response shapes of the pilot, sources, work, retention and staff operations are translated from the shared zod definitions in `lib/valopay-schema` by the generator. `pnpm run test:operations` checks close reviews, source quality, signed ingress, work receipts, staff grants, encryption, recovery manifests and retention. PostgreSQL suites exercise persisted routes, concurrency and restricted runtime roles. Console and browser checks cover workflows, stale edits and uncertain responses. CI uses disposable synthetic data and requires no Paystack or managed key credentials.

## Workflow recovery and Finance review

Pending import corrections appear in My work under reviews with their original waiting date, assigned reviewer and direct proposal link. Close blockers link to the same proposal. Administrators can reassign pending corrections or close reviews to an active independent Finance reviewer with a reason. Neither accepts a demo persona (403): one browser switching personas is one person, so a persona could never decide the proposer's or preparer's work. Reassignment records an immutable event; the original proposal or prepared snapshot never changes. A decision based on an earlier assignment or review version is refused. Reassignment does not itself approve evidence. A correction whose recorded reassignments disagree, which only damaged data holds, cannot be decided or reassigned; My work shows it with a notice, escalated to administrators, and the lender's other work and the batch's other corrections load as usual.

Close review history is searchable and paged. A direct close link loads its complete stored report even beyond the most recent 25 closes. The financial statement presents totals, matching and unresolved items, source completeness, settlement and currency evidence; technical JSON remains available separately. Older reports remain inspectable, but decisions still require current source evidence and independent approval.

The console records an opaque submission key, method, route and page under its current actor, role and lender before a recoverable write. It stores no form body in browser storage. Reloading the original form checks the server for that exact request and prevents a new submission while the result is uncertain. Recovery uses the server's original payload. Cancelling an absent request writes a terminal fence so a delayed original cannot execute afterwards. Clearing local form fields alone does not prove a server request was cancelled. Different staff, roles and lenders cannot recover each other's keys.

Private-file cleanup after sandbox expiry uses migration 013 and the service worker described in [deployment](deployment.md). The sweep retains workspaces with any running export, even an expired lease, until export recovery settles it. Previously attempted, non-ready files get a five-minute delay before their first cleanup attempt to let bounded interrupted uploads settle. This allowance does not establish certainty about indefinitely delayed external storage writes. These improvements do not configure Paystack, a scheduled host, an independent monitor, outbound alert delivery or a hosted restore.
