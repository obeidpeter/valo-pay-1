# Source interpretation and traceability

The [machine-readable matrix](traceability.json) preserves all **251 requirement identifiers: 171 legacy and 80 Connected Banking requirements**, together with **F01–F18**. Its technical baseline is commit `cd9d81c665ca08c29429e26bb3ed0d78863b5966` in `obeidpeter/valo-pay`. It records source identity, short engineering summaries, related code, contracts, test sources, dependencies and remaining acceptance. Source presence, test execution, deployment and independent acceptance are separate fields.

The five supplied Word documents were extracted read-only, including body paragraphs and tables. The Technical Requirements v2.1 catalogue was compared with the retained v2.0 architecture-review extraction: all 251 identifiers, normative bodies and acceptance criteria agree. The newer implementation-status statements remain dated evidence. The original Word files, financial workbook, complete extracted passages and historical architecture pack remain outside this public repository. No original document was overwritten or financial plan recalculated.

Paragraph and table locators are one-based OOXML body ordinals, **not rendered page numbers**. Each source has a SHA-256 digest. Each requirement also has a digest of its exact source requirement, acceptance criterion, dependency passage and priority/release passage; the public matrix contains a concise original summary rather than a reproduction of the controlled source. Original requirement text remains authoritative over the summaries.

## How to use the matrix

The `components` inventory identifies related baseline files and test sources. Its pointers carry the baseline revision and file digest, so later refactoring does not silently turn historical line numbers into current evidence. A related test file is not proof that every requirement in that component is covered or that the test ran. Requirement-specific fresh runs belong in `execution_evidence` and each requirement's `testing.fresh_evidence_ids`, with their actual scope and limits. Empty evidence lists mean no such evidence has been attached; they do not mean success or absence of supporting code.

The Technical Requirements feature selectors control technical expansion. Cross-document discrepancies are preserved below. Features not assigning a particular shared requirement do not exempt that requirement: tenancy, security, API, observability and operational obligations also apply across feature boundaries. Every operating gate remains unchanged by this matrix. Named accountable owners and formal acceptance are not invented.

Run `node docs/refactor-2026-09-29/validate-traceability.mjs` after editing the matrix. This validates identifier preservation, references, evidence classification and public-source boundaries. It cannot validate business approval, legal applicability, provider access or operational acceptance.

## Reviewed source-snapshot budget

The public-source snapshot's former 8 MiB aggregate cap was already smaller than the baseline it was meant to export. A read-only `git ls-tree -r -l -z cd9d81c665ca08c29429e26bb3ed0d78863b5966` measurement, filtered through the reviewed source allowlist, found **1,232 allowed files totalling 11,659,855 bytes**; the largest was 972,719 bytes. The six newly allowed programme artifacts do not exist in that baseline and therefore do not account for the pre-existing excess. The staged programme measurement before the budget adjustment was 1,238 files and 12,337,105 bytes.

`scripts/github-snapshot.mjs` now uses an explicit **16 MiB aggregate budget**, retaining the **2 MiB per-file cap**, exact UTF-8 checks, credential detection, binary/link refusal and all private-source exclusions. This is a bounded source-publication size review, not permission to upload private documents or skip scanning. Synthetic fixtures verify that an allowed 12 MiB source collection fits and an allowed 17 MiB collection still requires a separate review. No upload was performed by these checks. A future aggregate increase requires another measured review; the six programme paths are individually allowlisted rather than admitting their whole directory.
