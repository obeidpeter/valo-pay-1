# Repository assessment and scope disposition

29 September 2026. The starting revision is `cd9d81c665ca08c29429e26bb3ed0d78863b5966` (merged PR #77), repository `obeidpeter/valo-pay`. This assessment covers the mandate's areas; it does not equate source inspection with full requirement acceptance. The [traceability matrix](traceability.json) records all 251 requirements and F01–F18, including untouched requirements and their remaining acceptance. Fresh combined checks, measurements and release identity belong in the programme release record; historical audit reports remain unchanged.

## Findings that determine the implementation

1. **Unnecessary capability dependency.** `artifacts/api-server/src/domain/actions.ts` needed `resolveUnknownCheckout` but imported the whole Connected coordinator, bringing Credit and Cash implementations into the Core runtime graph. The [backend package](backend-package.md) extracts the checkout boundary, retains compatible exports and adds a transitive dependency guard. This is a measured dependency improvement, not a claim of reduced operational latency.
2. **Inconsistent current permission validity.** `connected-credit-service.ts::currentGrants` used creation time in place of a stored `validFrom`; its read model also omitted the positive numeric version condition used elsewhere. The failing future-start regression established a real authority defect. The backend package shares the narrow validity predicate while preserving capability-specific scope checks, redacts unavailable retained results and refuses stale receipt disclosure. It does not replace authorisation with a general permission boolean.
3. **Missing credit evidence presented as zero.** Credit amount presentation used numeric coercion that could turn missing liquidity into a number. The experience package preserves unknown values explicitly; missing evidence must not look like a zero balance. This is an evidenced display defect, distinct from changing affordability, model or lender policy.
4. **Commercial dates disagree with the source contract.** Baseline `billing.ts::discountRateFor` relies on a fixed discount year. BIL-02 instead requires reviewed contractual dates covering the pilot and bridge. The user approved the reviewed-date approach on this programme. `domain/commercial-terms.ts` and its consumers implement that separately approved behaviour change, with historical invoices preserved. See SRC-05 in [source notes](source-status-notes.md); passing a fixture does not approve any customer's price or dates.
5. **Navigation and payment state need explicit meaning.** Cash sections benefit from shareable URL state, and payer progress must distinguish submission from confirmed receipt and settlement. Shared evidence disclosure, progress presentation and domain-focused Credit components improve task understanding while keeping server authority and existing recovery identities.
6. **Traceability was not an executable maintained control.** The supplied documents and historical review retain the catalogue, but they do not check later code changes. The new matrix and validator preserve IDs, source provenance, gate identity, feature mapping and evidence distinctions. `check:traceability`, `test:pure` and the complete offline runner now execute the validator.

## Residual boundaries and continuation

The repository already contains substantial storage, API, worker, recovery and security controls. Reusing them is deliberate; replacing the stack or making every evidence payload a new table would increase change risk without satisfying a demonstrated missing contract. `repository/core.ts` remains a substantial composition point, and legacy open record containers remain technical debt. Neither is labelled a safety failure based on size or syntax alone. New code should use typed known-record access and narrow repository/capability interfaces.

The v1 legacy-key compatibility gap, full database conservation acceptance, production independent dispatch evidence, genuine multi-person approval, provider access, physical-device research and hosted recovery require their own evidence or migration decisions. Optional financial projection and synthetic instruction rehearsals do not close those gaps. No existing live gate is advanced by the implemented refactoring.

Before claiming a package complete, use its final combined build/contract/test result and compatible rollback instructions. Before any shared deployment, bind those results to the exact reviewed commit and environment. Do not infer hosted acceptance from a local benchmark, a successful merge or a previous task's summary.
