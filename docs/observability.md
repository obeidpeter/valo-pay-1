# Observability

A review of what an operator can see of the API and the console, made after the security and internationalisation reviews and in the same manner: read the surface, test what can be tested here, fix what is this repository's to fix, and write down what was found, what changed, what is accepted and what belongs to the host. It answers four questions: is the service healthy, what happened to a request a person is reporting, why did a close not run, and how long do the heavy operations take.

## Scope and method

The API's logger and request logging (`artifacts/api-server/src/lib/logger.ts`, `app.ts`), the error handler, the process entry point and its lifecycle, the close scheduler, the export route, the refusals (origin, request limit), the health route and the database module; the console's failure surfaces (the workspace failure page, problem notices, the error boundary). Every log call was read; the built API was run against PostgreSQL to look at its lines and answers and to stop it with a signal; the offline test `artifacts/api-server/tests/observability.test.ts` reads the log back from a file and pins the behaviour.

## What is sound

- **Request lines.** One structured line per request with method, path, status and time; the query string is never written, nor cookies or authorisation headers (redacted), nor request or response bodies.
- **The scheduler.** Every close pass carries a correlation id (`job`, `runId`) on its lines, each lender's close is its own line with the close id and its lateness, and a failure names the lender and the error (NFR-OBS-01).
- **Alerts from state.** The overview's alerts feed (a missed close, a broken audit chain, unallocated money past its threshold, an instruction in observation mode) is computed from the lender's records, so it needs no monitoring pipeline to be right (NFR-OBS-02).
- **Levels.** `LOG_LEVEL` sets the level; the console keeps a service failure's internals off the screen and shows a refusal in the rule's own words.

## Findings, and what changed

| # | Finding | Kind | Status |
| --- | --- | --- | --- |
| 1 | Requests were numbered by a per-process counter that was never returned, so a person reporting a failure had nothing to quote and an operator nothing to search for. | Correlation | **Fixed.** Every request has an id: 16 random hex characters or, where the deployment says its edge sets `X-Request-Id` on every request (`VALOPAY_EDGE_REQUEST_ID=on`), the edge's own when it is a plain token (8–64 characters of letters, digits, `.`, `_`, `-`). A client's header is never taken otherwise, since a client could reuse a reference someone had quoted (23 September 2026 audit, security item 8). It is on every log line of the request, on the answer as `X-Request-Id`, and in every error body as `requestId`. |
| 2 | A programming error was logged with its name and message only; the stack, which is what locates it, was dropped. | Diagnosis | **Fixed.** A failure (`event: request.failed`) is logged with `err` and its stack; the answer stays general. |
| 3 | A refused or rejected request was visible only as a status on its request line; the reason was nowhere. | Diagnosis | **Fixed.** A rejection is one info line (`event: request.rejected`, `status`, `reason`); a cross-origin or malformed-origin refusal is a warning (`event: request.refused`, `reason`), and the request limit is a warning once per client and window, so a flood does not double its own log. |
| 4 | `/api/healthz` said "ok" and nothing else; there was no readiness answer, so a host could not tell an instance that cannot reach its database from one that can. | Health | **Fixed.** `/api/healthz` (liveness, never touches the database) reports the build, the start time, the uptime and the scheduler's state, tick count, last tick and last pass that found work. `/api/readyz` makes one bounded round trip to the database (2 s) on its own connection, so a busy request pool does not read as an unreachable database, and answers 503 `degraded` while it fails; the reason goes to the log, not the answer. The round trip reads the catalogue too, so a database that answers but lacks a table or a column this build needs (a migration not yet applied), or a unique index or check constraint the schema declares (an integrity guard, which a push stopped part way could leave missing), is not ready either (`checks.schema.status` `incomplete`). A missing read index leaves the instance ready (`indexes_missing`), since every request still works, only slower, and failing would take every instance out of rotation. The log names what is missing and where it comes from; the answer does not. Both answer without Clerk, before sign-in is checked. Probes share one readiness check while it runs, and its answer is reused for a second after it finishes, so a burst makes one round trip and cannot starve the check's connection into 503s; each client network may make 120 health checks a minute (23 September 2026 audit, security item 6 and operations item 4). |
| 5 | Log lines were pretty-printed and coloured unless `NODE_ENV=production`, which no start command sets; on an unknown host the log would have been for a person, not a collector. | Format | **Fixed.** JSON on stdout unless `NODE_ENV=development` or `LOG_FORMAT=pretty`; `LOG_FILE` writes synchronously to a file instead, which is how the offline test reads the lines back. |
| 6 | Nothing said which build a line or an answer came from. | Provenance | **Fixed.** The build script stamps the commit and the build time into the bundle; every line carries `service` and `build`, as do the health answers and the start line. From the source tree the build is `source`. |
| 7 | An error on an idle database connection is emitted on the pool; unheard, that event ends the process. | Availability | **Fixed.** The process listens (`event: database.pool_error`) and the pool replaces the connection. |
| 8 | A stop signal ended the process at once, cutting requests in flight and any close pass in progress, and a crash nothing caught wrote a bare stack to stderr. | Availability | **Fixed.** On SIGTERM or SIGINT the process stops accepting, finishes the requests in flight, ends a close pass after the lender close in progress, ends the pool and exits, within a 10 s deadline (`event: server.stopping`, `server.stopped`, `server.stop_timeout`); an unhandled rejection or uncaught exception is a fatal line (`process.unhandled_rejection`, `process.uncaught_exception`) before the exit. A close cut by the deadline rolls back with its connection and runs as a catch-up after restart (NFR-AVA-02). An export attempt in progress is cancelled and its job returned to the queue (`export.job` with `status: released`), or it keeps its lease for recovery if that write cannot be made (`interrupted`); a stop never marks an export as failed. |
| 9 | A quiet scheduler pass wrote nothing, so a stopped scheduler and an idle one looked the same, and a pass had no duration. | Scheduler | **Fixed.** Each pass that found work is one line (`event: close.run`) with its duration and counts; a quiet pass is a debug line; the state, tick count and last pass are on `/api/healthz`. |
| 10 | An export's generation time was stored on its record but never logged. | Timing | **Changed.** It was logged as `export.generated` until exports became background jobs. Now `export.queued` marks a request queuing one and `export.job` each worker attempt with its outcome, and the size and generation time are on the ready export's status answer (`byteLength`, `generationMs`), not in the log. |
| 11 | The console's failure notices gave the time of a service error but not the request. | Console | **Fixed.** A problem notice for a 5xx ends with "Reference <id>", and the workspace failure page gives the time and the reference together; a refusal keeps the rule's own words. |
| 12 | An address under `/api` that no route answers returned the framework's HTML page. | Answers | **Fixed.** A JSON `Unknown resource.` with the request id. |
| 13 | No database limits: ten requests waiting on one busy lender took the whole connection pool, an unrelated tenant's fast page waited 4 s and `/api/readyz` failed. A request also waited for a free connection for ever. | Availability | **Fixed.** Every transaction sets its own statement, lock and idle limits; a checkout waits at most 5 s; a tenant holds at most a third of the pool for its lenders and one lender at most half of that (counted per workspace and lender), and further requests wait without a connection; reads answer from a snapshot and never wait for a lender's lock; readiness has its own connection. Busy lenders of three tenants at once can still fill the pool; see `docs/DATABASE_SECURITY.md`. A request turned away is a 503 with `Retry-After` (`event: request.busy`). |
| 14 | A connection the database ended while a request held it (an administrator, a restart, the idle limit) was an unheard client error that ended the process, and the request was answered 400 with a driver message. | Availability | **Fixed.** Every checkout listens for its connection's errors and hands a broken connection back to be destroyed; the request is a 503 (`connection_lost`, or `idle_timeout` at the idle limit) and the process carries on. |
| 15 | A bad setting ended the process with a bare stack from whichever module read it (`LOG_LEVEL=verbose`, `VALOPAY_DATABASE_POOL_SIZE=1`, `PORT=70000`), or not at all: `VALOPAY_CLOSE_SCHEDULER=OFF` ran the scheduler, and an invalid `VALOPAY_RUNTIME_ISOLATION` left liveness at 200 while the export worker logged an error every 1.5 s. With the database unreachable the worker wrote about 2,400 error lines an hour. | Configuration | **Fixed.** The settings are checked once, before any module reads them (`artifacts/api-server/src/lib/startup-config.ts`): a value outside its rule is one fatal `config.invalid` line naming each setting, never its value, and exit status 1. The scheduler's switch takes `on`, `off` or `external` in any case and refuses anything else. The export worker logs `export.queue_error` once when its queue stops answering and `export.queue_recovered` once when it answers again, and meanwhile looks less often, from 3 s doubling to a minute. |
| 16 | Malformed input from any client (a path whose percent-encoding cannot be decoded, a body that cannot be decompressed or is nested thousands of levels deep) was a 500 with two error-level lines per request, so an anonymous client could fill the error log at will; an outage of private storage or the identity provider was a 500 as well; and an error a dependency raised without a status, such as a missing identity-provider key, was a 400 logged as a rejection at info. | Diagnosis | **Fixed.** Malformed input is a 4xx refusal logged at info (`event: request.rejected`); a service out of reach is a 503 with `Retry-After` (`event: request.unavailable`); a dependency's error without a status is a 500 at error level (`event: request.failed`). |
| 16 | The scheduled closes and export generation ran on the event loop that answers requests: a lender's first close at pilot scale held every tenant's requests and `/api/healthz` for seconds (3.5 s at 1,000 customers), and a month-end close for 8 s. | Availability | **Fixed.** They run on the API's background worker thread (`artifacts/api-server/src/background.ts`), which has its own pool of three connections: a 3.6 s first close of 20,000 records left health probes from another process answering within 16 ms. The thread's lines are written by the main thread and carry `thread: background`; it posts the scheduler's state to the main thread for `/api/healthz` and the console; a crash is `background.crashed`, and the thread starts again after a wait that doubles from a second to a minute; a stop lets the close in progress finish and returns exports to the queue before the thread ends (`background.stopped`). |

## Reading the log

Every line the logger writes is JSON with `level` (20 debug when `LOG_LEVEL` admits it, 30 info, 40 warn, 50 error, 60 fatal), `time`, `pid`, `hostname`, `service` (`valopay-api`) and `build`. A line the background worker thread wrote (the scheduled close, the daily audit check and the export worker) also carries `thread` (`background`); the main thread writes it for the thread, so the two threads' lines never interleave. A request line has `req.id`, `req.method`, `req.url` (the path, never the query), `res.statusCode`, `responseTime` in milliseconds and `msg` `request completed`, or `request errored` for a 5xx, at error level except for a 503 with `Retry-After` (a database limit), which is a warning so a busy moment does not page anyone. Lines the request wrote itself carry the same `req`. A line with an `event` has one of these; `scripts/check-docs.mjs` fails when the code logs an event this table does not list, or the table lists one the code does not log:

| Event | Level | Fields | Meaning |
| --- | --- | --- | --- |
| `request.rejected` | info; warn for a database safety constraint (409) | `status`, with `reason`, `issues` (the number of validation problems) or `code` (PostgreSQL's) | A rule refused the request in its own words (400, 403, 409, 410, or 429 with its `Retry-After`), the body could not be read (400, 413, 415; `reason` is the parser's type, such as `charset.unsupported` for a body in a character set other than UTF-8, zlib's code such as `Z_DATA_ERROR` for a Paystack test delivery that cannot be decompressed, `content_type` for a body that is not JSON, `content_encoding` (415) for a compressed body, refused before it is read, or `nul_character`, `unpaired_surrogate`, `nesting_depth` or `too_many_values` (413: more than 10,000 values) for a body refused before anything reads it, the last two from its bytes before it is parsed), the path's percent-encoding cannot be decoded (400, `path.malformed`), validation failed (400, `issues`), a database safety constraint refused the change (409, `code`) or PostgreSQL could not store its text (400, `code`). Any other 4xx a library marks safe to expose is logged here too, never as a failure. |
| `money.calculation_refused` | Warn | Exact monetary calculation cannot fit the supported amount or rate limits; HTTP 422. Logs the error code, never input values. |
| `request.refused` | warn | `reason`: `origin`, `origin_malformed`, `rate_limit`; with `rate_limit`, `limit`: `network`, `principal` or `health` | The shell refused it before any route ran. A rate limit is named once per client and window: `network` is a client network's 1,200 requests a minute, `principal` a person's, a served sandbox's or an unknown client's 300, and `health` a network's 120 health checks. |
| `request.failed` | error | `err` with stack; `code` when the error has one, `upstreamStatus` when a service it depends on answered with an error | The service itself failed, including an error a dependency raised without a status (such as a missing identity-provider key); the answer was a general 500, or a 502 when a service it depends on answered with an error of its own. | `request.unavailable` | error | `status`, `reason`, `err` | The application refused the request because a service it needs is unavailable or not configured (502, 503, 504), or an export failed its checksum (500); the answer keeps the status and the reason. A service it depends on that could not be reached (a network failure on the way to private storage or the identity provider, or the identity provider's API sending no answer or answering that it is overloaded) is a 503 with `Retry-After`; a runtime error of its SDK, such as a missing key, is a `request.failed`. |
| `operation.rejection_unrecorded` | warn | `err` | A request the service refused, or that failed, could not have its operations-journal entry settled (closed, or read for the answer). The size and generation time of a ready export are on its status answer (`byteLength`, `generationMs`), not in the log. |
| `export.worker_error` | error | `exportId`, `err` | The worker could not claim a job, for example with the database unavailable; the job stays as it was and a later poll tries again. |
| `export.queue_error` | error | `err`, `retryInMs` | The worker could not read the queue. Written once when this starts, not at every look: the worker looks again after 3 s, then doubles the wait up to a minute until the queue answers. |
| `export.queue_recovered` | info | `failures`, `unavailableMs` | The queue answers again after `failures` failed looks over `unavailableMs`; the worker is back to a look every 1.5 s. |

Not everything the process prints comes from the logger. At startup Node writes a deprecation warning (DEP0040, for the `punycode` module a bundled dependency loads) to stderr, once for the main thread and once for the background worker thread. A missing or malformed setting is not a bare stack: the start-up check writes its `config.invalid` line, in the logger's shape, before anything else loads. With development-instance Clerk keys the Clerk SDK prints a three-line telemetry notice on stdout, as plain text among the JSON lines, once per process, unless `CLERK_TELEMETRY_DISABLED=1`, which the deployment sets and every pilot host should set (`docs/deployment.md`). A start through `pnpm run` prints pnpm's own command line first (`dev` also prints the build's output, and pretty-prints the log). A collector should parse the lines that are JSON and keep the others as they are.

**Tracing a report.** A person quotes the reference from a notice or the failure page; it is `req.id`. Every line of that request shares it: the request line, the rejection or failure line, a refusal. A scheduled close is traced by `runId`; a person's close is a request like any other, with its audit entry in the lender's log.

**What to watch.** Any line at level 50 or above, including `request.busy` with `limit` `statement_timeout`, `idle_timeout`, `pool_timeout` or `connection_lost` (`pool_timeout` alongside `lender_busy` for three or more tenants means their lenders filled the pool between them); bursts of `request.busy` with `lender_busy` or `lock_timeout`, which mean one lender's requests are queuing behind a long change; `request.refused` with `reason: rate_limit` in a burst; `sign_in.off` at start-up on a host where people sign in; `readiness.failed`; on `/api/healthz`, `scheduler.state` other than `running` on an instance that should schedule, or other than `external` on a host whose closes run from a scheduled job, a `scheduler.backlog.checkedAt` there older than three minutes, or missing from an instance up for more than 80 seconds, a missing or stale `lastSuccessAt`, a `lastErrorAt` after its latest success, or `scheduler.backlog` with `failing` or `overdue` above zero, which stay there until each of those lenders' closes succeeds (its `publicSandboxes`, a visitor's synthetic lenders, are worth a look but never an incident); `close.run` with `failed` above zero; `export.job` with `status: interrupted`, which means an export waits up to five minutes for its lease, and `requeued` repeating for one export, which means another change keeps its lender for long stretches; `export.queue_error` without a later `export.queue_recovered`, or `export.worker_error` repeating, which means queued exports are not moving; `config.invalid`, which means an instance did not start; `background.crashed`, above all the same crash repeating with a growing `crashes`, which means scheduled closes and exports are not running on that instance; `close.one_shot` with `exitCode` other than 0, on a host whose closes run from a Scheduled Deployment, and `close.backlog_failed` on its web instances; `audit.daily_check` at error level, which means a lender's audit chain is broken and its overview and closes carry the critical `audit_chain_broken` alert, and `audit.daily_check_failed`; `close.run` with `auditChecksLeft` above zero pass after pass, which means close passes spend their budget before the day's audit checks; `workspace.sweep_file_left`, repeated cleanup availability warnings, and a growing or ageing backlog in `pnpm run check:export-cleanup`; `operation.rejection_unrecorded`, which leaves a refused request pending in its person's journal until they retry or cancel it; a lender whose failure line repeats with a growing `failures` count, which means its close keeps failing and it waits up to an hour between attempts; the distribution of `responseTime` on request lines, and of `generationMs` on ready exports' status answers. `lastTickAt` means a check started, so it must not be used alone as evidence that a check completed.

## Daily-close service status

The scheduler records `lastTickAt` when a pass starts, `lastSuccessAt` when its scan and loop return, and `lastErrorAt` when the pass itself fails. It runs on the background worker thread, which posts each of these changes to the main thread, where the health answer and the console read them; a thread that crashed counts as a failed pass (`lastErrorAt`) until the restarted thread's first pass succeeds. A later successful pass clears the service error. A returning pass can still contain individual lender failures, and a successful service check is not a successful close for every lender. So each pass ends by reading from the database what is still owed, and the health answer carries it as `scheduler.backlog`, counts that name no lender: `failing`, the lenders with a failed scheduled attempt recorded at their pending time (`settings.closeRetry`), and `overdue`, the lenders whose automatic close is on and whose pending close is more than 30 minutes (`lateAfterMinutes`) past its time, whatever the reason: failing, held by a request or another instance, left by a pass whose budget ran out, or still catching up missed business dates one a pass. Neither counts public anonymous sandboxes, the synthetic lenders a visitor's sandbox is seeded with or creates (`settings.anonymousWorkspace`, which a signed-in person's and a staff pilot's lenders never carry): a visitor's own data can make its close fail, so their own `failing` and `overdue` are `scheduler.backlog.publicSandboxes`, which the monitor gives as warnings. Only something done to that lender takes it off: a close, by the scheduler or a person, or a change to its close time or automatic close in Settings (the pause of an idle sandbox included); another lender's close, a quiet pass or a restart does not, since the next pass reads the database again. `backlog` is null until the process's first pass has read it, and keeps what was last read while the scheduler is stopped or failing. With `external` no pass runs in the process, so its background worker thread makes the same read every minute and the health answer carries each as `scheduler.backlog`, with `intervalMs` saying how often (null with `external` from a build before this read): a scheduled job that has stopped running shows as overdue closes. A read that fails is logged (`close.backlog_failed`) and keeps the last one, whose `checkedAt` ages; these reads leave `lastTickAt`, `lastSuccessAt` and `lastErrorAt` alone, since they are not passes. `lastRun` is still the last pass with work, which a later pass with work replaces, with `failed` counting that pass's failures alone, public sandboxes' included; the lender's log lines say why its close failed.

A pass reads due lenders in batches of 25 until none is left or 45 seconds have passed (three quarters of the interval when that is shorter), so a backlog drains in one pass rather than 25 lenders a minute, and a stop ends it after the lender close in progress. A lender owed several missed business dates gets one catch-up close per pass, oldest first, so its backlog never holds the other lenders back; the `close_missed` alert names the dates still owed. Staff and signed-in lenders come before anonymous sandboxes; within each, lenders being retried come after the rest, then one lender per workspace per turn, then the earliest time. A failed close is recorded on the lender (`settings.closeRetry`: the pending time, the count and the next attempt, not the error) and retried after 2, 4, 8, 16 and 32 minutes, then hourly; the close stays pending, and missed after 30 minutes, until an attempt succeeds, so the `close_missed` alert shows meanwhile. An anonymous sandbox older than seven days that nobody has changed for seven days has its automatic close switched off instead of run, with an audit entry, and the console says so.

The console combines this process status with the scoped lender schedule through `artifacts/api-server/src/lib/valopay-close-views.ts` and `artifacts/api-server/src/domain/effective-close-schedule.ts`. Its `closeSchedule.automatic` is true only for a requested schedule with a running service and a recent successful check. Before the first success it says starting; a failed pass or a heartbeat older than the greater of two minutes or three tick intervals removes the advertised next run. An intentionally off service also removes it, and a missed close is not reported there, since nobody runs automatic closes. A service whose closes run from a separate scheduled job (`external`) removes the advertised next run too, as this process cannot see the job's, but reports a missed close as a running service does: the `close_missed` alert names the business dates still owed, and the console says daily closes run from a scheduled job and, once one is missed, asks for a daily close and a check of the job. The completed-close time and trigger come only from this lender's records; another lender's identifiers, run results and failure text are not included in the console projection.

Heartbeat freshness compares the API host's check timestamp with its internal `observedAt` clock. The lender's due time, overdue duration and close records continue to use the database clock. This prevents clock differences between the database and API host from being mistaken for a stale worker. Overview, Reports and Settings refresh every 60 seconds while active and show the service-check time separately from the last completed close. Saving the lender's schedule preference does not start the service, and these process-local observations are not an availability guarantee or a fleet-wide health check.

## What was left out

An external one-shot probe and incident/recovery sender are now implemented in `scripts/monitor-valopay.mjs`. It has a local delivery rehearsal and a selected email recipient, but no configured external email service or recurring host schedule. See `docs/operational-rehearsals.md` for the setup and exact verification boundary.

- **No metrics endpoint.** The lines above carry every count and duration a dashboard needs, and the host's log tooling aggregates them across instances; an in-process counter on an autoscaled instance would answer for one instance only and read as the whole.
- **No distributed tracing.** One service and one database: the request id is the trace.
- **No error beacon from the console.** A page error is written to the browser console with its component stack and shown with the time and the address; a service failure carries the reference. Collecting browser errors is a product decision that involves the people using it.
- **4xx at info, not warn.** A refusal is the rule working; only the shell's refusals are warnings.
- **Retention, shipping and alert routing belong to the host**, as do the readiness probe's schedule and what it does with a 503. The Replit deployment's start-up health check is `/api/readyz` (`artifacts/api-server/.replit-artifact/artifact.toml`), so a build whose database lacks a table, column, unique index or check constraint it needs does not go live (`docs/deployment.md`).
