## Implementation boundaries

- `GetStarted` uses the existing scoped `/pilot/progress` read only while expanded. No new endpoint, heavy overview read, polling job or state mutation was added.
- Completion comes from the existing import/reconciliation/close evidence, not a local click. The checklist clearly describes shared lender progress, not the current person's accomplishment.
- Browser storage contains the open/collapsed preference and reading position only. Keys are scoped by the existing viewer scope (or actor fallback) and lender; no financial drafts or source rows are stored.
- The initial checklist stays optional and can be resumed. No self-selected goal assigns a role or changes current authority.
- Sample imports, provider configuration, real staff acceptance and independent approvals remain separate. No live readiness, payment, accounting or tax execution is claimed.
- Existing Overview metrics, alert destinations, queues and daily-close status remain available after the next-task card. No business or pricing rules were changed.

## Complete synthetic first Collections journey

`tests/beginner-collections-journey.test.tsx` exercises the rendered application against the real in-memory domain operations, as Finance for an authorised empty sample lender. The clock matches the instalment date in the shipped sample. Lender provisioning is a fixture boundary because this test adapter has no lender-creation endpoint; the journey does not claim to verify account creation, identity-provider login or live data ingestion.

1. Enter Overview, open the optional getting-started steps and follow the import task.
2. Load the actual customer sample and deliberately remove the consent source. Save/check it: the invalid source row and field are named, committing is disabled, and no customer exists yet.
3. Leave for Overview, see Needs attention, return to the saved batch and recover the exact CSV. Use Correct CSV, restore the consent source and save/check. The customer still does not exist until the explicit one-time commit.
4. Import the format-matched sample instalment. Import two statement observations: one identifies the sample payer and matches its instalment's amount/date, without an instalment reference; the other remains unidentified. Each batch is checked and committed once. Importing evidence alone creates no payment allocation.
5. Run reconciliation. Inspect the Finance R5 proposal's payment reference, instalment, settlement status and recorded explanation. Attempt confirmation without a reason: no action is sent and focus returns to the required reason. Enter a reason and confirm once.
6. Find the allocated receipt in the customer's history. Open the separate unidentified receipt's unallocated-payment exception and its Case & handover page. The case remains open; coordination does not silently resolve or allocate anything.

Assertions also preserve the other lender unchanged, maintain the Finance role, reject unexpected HTTP failures, and check that sample identifiers were not saved in browser storage. This is an engineering walkthrough, not independent-user evidence.
