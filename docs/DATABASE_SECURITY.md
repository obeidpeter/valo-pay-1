# Database security boundary

## Scope and rationale

Valo Pay remains an isolated **synthetic observation sandbox**, not an approved system for real lender/customer data. Its runtime security boundary is the application's scoped repository. This deliberately replaces a custom PostgreSQL role, RLS policies and a record-protection trigger that the observed managed publishing path did not reproduce faithfully. An opt-in restricted runtime adds forced row security again for a separately commissioned staging schema (see Development setup and publishing); it is off by default, and the preview database has not been commissioned with it.

By default the database connection is privileged. Explicit application checks **do not** provide the same independent barrier as a non-bypass database role with correctly configured RLS. A leaked database credential, malicious server code or an unscoped query can bypass application authorisation and immutability. Do not describe this redesign as preserving database-enforced isolation.

## Enforcement

- Identity comes from verified Clerk request context or the existing high-entropy anonymous sandbox cookie (`__Host-valopay_sandbox` behind TLS, which no other host can set), not a caller-supplied principal/workspace identifier. An absent or malformed sandbox cookie creates a separate synthetic workspace; it never grants access to an existing workspace, and a request carrying two different sandbox tokens is refused. New anonymous sandboxes are limited to 20 an hour per client network (an IPv4 address or an IPv6 /64), 60 per IPv6 /48 and 300 per API process, on top of the general request limit, and the cookie lifetime (30 days) slides with each visit. Where `VALOPAY_EXPIRED_WORKSPACE_CLEANUP=on`, as the deployment sets it (`docs/deployment.md`), an anonymous sandbox older than 30 days with no change by a person in that time becomes eligible for deletion, and it is deleted only when a new anonymous sandbox is created: that request removes up to five eligible sandboxes, oldest first (their idempotency answers, records, lenders and, by cascade, operations journal, then the workspace), so an eligible sandbox stays until enough new visitors arrive. The sweep first locks every lender of the sandbox without waiting and leaves a sandbox whose lender a scheduled close, the export worker, a test delivery or a request holds for a later sweep, so it never waits for or deadlocks with them; activity is read from the audit chain, so entries by system actors (the seed, the scheduled close) never keep a sandbox alive, and signed-in and staff workspaces are never swept. Once the deletion has committed, the same request removes the swept lenders' export files from private storage, each only if its ownership metadata names that export and lender; a file it cannot remove is named in the log for an operator (`workspace.sweep_file_left`) and never undoes the sweep. Without the setting (the development workspace) nothing is deleted.
- Database access is confined to explicitly reviewed modules by `scripts/check-db-boundary.mjs`: the private scoped repository under `artifacts/api-server/src/lib/repository/`, the lender-scoped export job store, runtime isolation and the financial projection subordinate to the repository transaction. `valopay-store.ts` is an explicit public facade; application code cannot import repository internals. The private core owns the context-to-session map, transactions and locks, and supplies typed capabilities to feature factories. The allowlist names individual modules rather than granting access to any new file in that directory. The guard also rejects raw queries and connection settings elsewhere; the startup check may read `DATABASE_URL` solely for configuration validation. Workspace membership, selected merchant ownership and record predicates must still be checked explicitly. Routes/domain code must not obtain raw clients or unrestricted query functions. Negative fixtures check facade leaks, internal imports and database access bypasses. This is a source-maintenance control, not a sandbox against malicious code.
- With `VALOPAY_STAFF_ACCESS=staging`, identity is a verified Clerk session instead: every staff request loads the organisation's workspace and the caller's membership in its own transaction, holds them locked through commit, and passes them to the access and MFA check in `docs/pilot-security.md` before it reads anything else.
- The scheduled daily close is the one platform-initiated write path. It runs in the API process, on its background worker thread (`artifacts/api-server/src/background.ts`) through the same repository modules, one merchant per system transaction (`inMerchantAsSystem`), scoped to that merchant's own workspace and principal so every repository predicate still applies, with the merchant row taken `FOR UPDATE ... SKIP LOCKED` so it never queues behind a request and two processes never close the same lender at once. It writes through the same load, audit and save path as a request, under the actor `System · scheduled close`. Which merchants are due is read from the server-owned `settings.nextCloseAt` cursor. Two small service writes sit outside a merchant transaction: a lender's first `nextCloseAt`, written only where none is set, and after a failed close the `settings.closeRetry` record (the pending time, the number of failed attempts and the next attempt; never the error text, because settings are shown to the lender's users), written with the row taken `FOR UPDATE SKIP LOCKED` so a lender held by a request is left alone. The scheduler's pause of an idle sandbox's automatic close goes through the same load, audit and save path as a close. The settings endpoint strips `nextCloseAt`, `closeRetry` and `closePausedForInactivityAt` from client input. A sandbox workspace holds at most five lenders; the count runs under the exclusive workspace lock that lender creation takes, so two creations at once cannot both pass it.
- Every workspace transaction holds the workspace's advisory lock: shared for ordinary work, exclusive for persona, team, lender-access and invitation changes. PostgreSQL grants advisory locks in arrival order, so a change waits only for the work already running and is never overtaken by later requests; if that work does not finish within the request lock limit, the change answers 503 with nothing changed. The workspace row is still locked after it (`FOR SHARE`, or `FOR UPDATE` for a change), so the expiry sweep's `SKIP LOCKED` skips busy workspaces. A principal transaction lock serialises only first-visit workspace creation. A mutation takes an exclusive merchant row lock (`FOR UPDATE`) that serialises state validation, allocations, idempotency and audit sequence generation across processes, not just within one Node instance. A read runs on one `REPEATABLE READ` snapshot and takes no merchant lock: it sees one consistent merchant state, the one from before any mutation still in flight, never waits for a mutation and never queues behind other reads. Its identity checks are a write's (the workspace lock and row, and a staff member's membership locked `FOR SHARE`), after which the transaction is made read only. A read that waited behind a change to its own workspace (a persona change, or a team change to the person's membership) finds the row changed since its snapshot and starts again once on a fresh one, so it meets the change as it did before; under runtime isolation a read whose membership changed that way is refused with 409, as before. Lock waits are bounded: a request waits at most 5 s for a lock and is then answered 503 with nothing saved. A tenant's requests for its lenders cannot occupy more than a third of a process's database connections, nor those for one lender more than half of that (`artifacts/api-server/src/lib/valopay-store.ts`, `artifacts/api-server/src/lib/lender-gate.ts`); the rest wait up to the lock limit without a connection. The lender a request names is read before the request is authorised, so the shares are counted per workspace (a staff organisation or a sandbox) and lender: a request that names another workspace's lender waits only behind its own workspace's requests. The shares limit one tenant's effect on others but cannot remove it: busy lenders of three tenants at once can fill the pool (three connections each of the default ten), and every other request then waits up to the 5 s checkout limit and may be answered 503. Requests that name no lender are not counted against any share. The background worker thread, which runs the scheduled closes and the export worker, has a pool of its own of three connections (one close and two export slots), so neither takes a request's connection nor waits for one; with readiness's one connection, an instance holds at most the pool size plus four (`docs/deployment.md`).
- Reads, business mutations, idempotent responses and audit appends share the authorised transaction. The repository retains its own original state for mutation validation, rather than trusting a snapshot supplied by its callers.
- The repository refuses record deletion, tenant/identity reassignment, immutable-evidence edits and changes to frozen approved/preregistered/closed versions. It validates linked records and final allocation totals before committing.
- Ordinary database foreign keys, primary/unique indexes, safe-integer money bounds and the due-item ticket floor provide additional protections. `/api/readyz` answers 503 while one of the unique indexes or check constraints the Drizzle schema declares is missing (`docs/database-migrations.md` says how to restore one). Cross-record allocation caps and evidence immutability are application rules, not triggers.
- Private exports are accessible only through authorised merchant metadata and checksum-verified downloads. The metadata is resolved inside the authorised transaction and the object is read after it ends, so no merchant lock is held for the duration of a download. Object storage is not part of the SQL transaction: an object uploaded before a later database failure can be orphaned, but must not become accessible through another tenant.
- Hash chains detect corruption relative to their stored history. They do not establish independent tamper-proof evidence against a privileged actor able to rewrite both history and hashes.

## Development setup and publishing

One opt-in database layer sits beside this boundary, and no migration of its runs during installation, build, startup or deployment. The restricted runtime is commissioned by hand with the migration owner, in a separate `valopay_runtime_staging_*` schema: `lib/db/migrations/005_runtime_isolation.sql` creates a restricted login, a non-login helper owner, scope helpers, a workspace guard and forced row security on the ten application tables, and `lib/db/migrations/006_runtime_isolation_scope.sql`, which the application requires, evaluates the same rules once per statement instead of once per row. Its isolation rehearsal (`docs/pilot-database.md`) applies both only in a disposable test schema. With `VALOPAY_RUNTIME_ISOLATION=staging` (which also needs staff access), the API refuses an elevated login (superuser, `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`, a membership of any role, such as `pg_execute_server_program` or `pg_read_all_data`, or `CREATE` on the runtime schema) and, in every transaction, compares the policies, helpers and guard, and every privilege the login holds on a table or a column in any schema (its own or PUBLIC's), with the reviewed set in `artifacts/api-server/src/lib/runtime-isolation-policy.ts`, refusing any other relation or function in the runtime schema too, such as a view another role owns, and answering 503 on any difference (`docs/pilot-operations-controls.md`). A privilege 005 does not grant, such as `TRUNCATE`, therefore stops staff access rather than passing as verified. It does not authorise real data; commissioning the identity service, the restricted login and managed keys on a host, and managed-host recovery testing, remain separate work.

The Drizzle schema defines the supported tables, foreign keys, checks and unique indexes. A fresh development setup uses the normal development schema push. Do not reintroduce custom security roles, policies or triggers as an undeclared setup prerequisite. The pull-request workflow creates the schema the same way inside a PostgreSQL 16 service container that exists only for its job and holds no application secret; that is a development push against a throwaway database, not a production migration path.

The existing development database transitions only after replacement application enforcement exists. Retiring the old objects must use narrowly scoped, reviewed development changes, preserve data and ordinary constraints, and never cascade-delete unknown role dependencies.

Production remains managed by the Publish flow, and nothing applies a migration automatically: no build-hook schema push, no startup-time DDL and no deployment step that runs one. The numbered files in `lib/db/migrations` are applied by hand, by the database owner, in order, before the build that needs them is published; `docs/database-migrations.md` is the one procedure for them (which are required, superseded or optional commissioning, the commands, verification and rollback). Inspect the freshly generated development-to-production diff before concluding a publishing problem is resolved: successful compilation does not prove migration fidelity. Review unexpected drops/renames and confirm all required ordinary constraints and expression/partial indexes retain their semantics. A push of an unchanged schema plans nothing, on a pushed database and on one built from the migrations (`artifacts/api-server/tests/schema-push.integration.test.ts`), so every statement a diff shows is a real change; earlier pushes dropped and rebuilt the in-flight and provider-event uniqueness guards and three foreign keys every time.

Removing the original role/policy dependencies addresses their specific missing-role failure mechanism. Only a subsequent user-initiated successful publish and post-publish checks establish that the complete publishing process works.

## Verification and residual requirements

- Run the database-boundary check, repository mutation/integration tests, API security regression script and existing smoke checks against the final schema **without** the legacy policies and trigger.
- Exercise foreign identities/merchant IDs, optional linked references, protected records, failed imports, transaction rollback, concurrent allocations/idempotency and audit sequencing, and authorised/unauthorised export downloads.
- Static boundary checks are a development safeguard, not a sandbox against malicious or deliberately obfuscated code.
- Real data remains blocked pending independent security assessment, production staff provisioning/MFA, documented hosting and legal prerequisites, tested recovery, and an explicitly approved production isolation design.

The reproducible checks are the ones in the README under "Checks and builds": `pnpm test` (database boundary, snapshot safeguards, repository guards, export collector and the golden suites), `pnpm run test:security-api` and `pnpm run test:smoke` against a running API, and the database-backed integration suites run with `VALOPAY_RUN_INTEGRATION=1`; the repository and scheduled-close suites (`pnpm run test:integration`) also run on every pull request against the workflow's throwaway database, while the export-stream and HTTP suites remain manual. The development transition evidence stays in the Replit workspace and is not part of this source snapshot.
