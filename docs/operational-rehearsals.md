# Operational rehearsals

The shipped sandbox remains synthetic. These checks exercise recovery, alert delivery and staff access on the restricted runtime without changing the deployed database, enabling the scheduler or sending collection instructions.

## Commissioning evidence before activation

Run `node scripts/commission-operations.mjs` with the same monitor settings described below. Set `VALOPAY_OPERATIONS_HOST_MODE` to `reserved-vm`, `autoscale` or `other`, reflecting the deployment configuration you have checked, and set `VALOPAY_MONITOR_EXPECT_SCHEDULER` to the intended `on` or `external` mode. The command makes only the public liveness and readiness requests. It does not create a workspace, run a close, send an alert or change configuration. `VALOPAY_OPERATIONS_REPORT` optionally writes the JSON report to a private operator path; the file is replaced atomically and created with owner-only permissions on systems that enforce them. Keep that directory outside the public source and restrict its Windows access permissions where applicable.

The report separates three kinds of evidence:

- **Configuration:** whether required delivery settings and an incident-state path exist and have valid syntax. Setting presence does not prove the provider key, sender or persistent storage works. The host mode is the operator's declared setting, not a remote hosting inspection.
- **Observations:** the liveness, database, required schema and scheduler state that this HTTP probe saw. A successful process heartbeat is distinguishable from an external host's answer, whose web instances report the mode and their own fresh read of what is still owed (`mode_and_fresh_backlog`; `mode_only` from a build before that read). An in-process scheduler on an Autoscale host is flagged because it stops when the host scales down. With `on` or `external`, `closeBacklog` gives the number of lenders whose close is failing or overdue, as the process last read them from the database, without naming any; either above zero is a blocker, and so is a build that does not report them (`scheduler_backlog_not_reported`): with `on` it shows a failed close only until a later pass with work, and with `external` it shows the mode alone. Public anonymous sandboxes' own counts are beside them, as `publicSandboxes`, and their warnings are never blockers. A process too young to have read them yet, such as an instance the check itself started on Autoscale, gives `closeBacklog` `pending` with the warning `scheduler_backlog_pending`, which is a blocker too, since the report then has no scheduler evidence: run the check again once the instance has been up for about a minute and a half.
- **Acceptance still needed:** an independently scheduled monitor with durable state; receipt and acknowledgement of a test alert; a measured isolated recovery of hosted database, private objects and required key access; and a close failure/recovery rehearsal. An external close job additionally needs actual completion evidence and a missed-run alarm seen to reach its operator: the monitor raises a job that has stopped running as overdue closes, but reporting `external`, or a report that observed no overdue close, establishes neither.

Exit status 2 means the completed check found a configuration or observed service problem; 1 means it could not produce a usable report. Exit status 0 means only that the configured settings and observations passed: the report still says `observations_passed_acceptance_required`, never that unattended pilot operation has been accepted. The script records no receiver URL, email address, key, private state path or customer record. `node scripts/commission-operations.test.mjs` checks the report and the actual command offline, including failures, the distinction between configuration and acceptance, and the command started through a symlinked path.

Worker observations are also required for commissioning. `background_not_reported` blocks a build that predates worker health, `background_unverified` blocks malformed observations, and `background_starting` or `background_cleanup_pending` blocks an instance whose first heartbeat/check has not arrived. Like every incident code, `background_cleanup_failed` blocks it until the failed files are removed, and `background_cleanup_needs_review` until each file parked for review is resolved (below). Inspect `observations.background` for enabled jobs, heartbeat, process-lifetime crash/restart counts and the last completed cleanup check. For the service sandbox, verify cleanup is enabled and its `lastSuccessAt` advances even with an empty queue. For a restricted tenant runtime, disabled service cleanup is expected. These HTTP observations establish neither durable queue emptiness nor successful file deletion; retain the separate `check:export-cleanup` report and storage recovery evidence.

## Incident and recovery delivery

The monitor checks reported background-worker health even when no close scheduler is expected. `background_not_running` covers a worker restarting, stopping, stopped or not started; `background_stale` covers a missing/old heartbeat; `background_cleanup_failed` covers the latest rejected cleanup pass, a deferred removal or a file waiting for a retry; `background_cleanup_needs_review` covers a file parked for an operator's review because its stored identity does not match, which no retry changes (below); and `background_cleanup_stale` covers a missing/old completed cleanup check. Invalid metadata is `background_unverified`. A normal first heartbeat has up to 45 seconds (`background_starting`), and the first cleanup check up to 195 seconds at its default interval (`background_cleanup_pending`). These warnings alone neither end nor repeat an incident. Each startup warning has its own window, which the probe gives in `startupWindowsMs`, keyed by the warning (`scheduler_backlog_pending` included; `firstReadWithinMs` and `backgroundReadWithinMs`, the longest worker window, remain for receivers that read them). With a startup warning the probe also names the worker that answered (`answeredBy`): its process's start (`startedAt` on `/api/healthz`), its own start, its restart count and its last crash, as the service reports them. The saved monitor state keeps when a run of probes that found nothing but startup warnings began (`pendingSince`), every startup warning the run has shown, with the window it first came with (`pendingWarnings`), and the first worker that answered and whether another has answered since (`pendingWorker`, `pendingRestarted`), telling workers apart only by what the service reports, never by the monitor's own clock; any other probe ends the run, including one from a build that omits worker status. Once the run has lasted longer than a warning's own window, that warning counts as its stale code (`background_stale`, `background_cleanup_stale`, or `scheduler_stale` for `scheduler_backlog_pending`): at once if the probe shows it, and otherwise only once the run has met another worker, so one worker's slow first cleanup check is not taken for a crash loop. A probe that names no worker, from a build before worker health, is judged by every warning of the run, as before. Within a run the judged codes only grow, so a crash loop opens an incident whichever warnings each probe happens to catch: a first read still missing after 80 seconds is judged then, not held back by a first cleanup check that may take 195. Two identical judged probes open the incident, which carries the run as `startupRun` (when it began, each warning it has shown with its window, and whether it has met another worker), so a code judged from an earlier probe's warning can be told from this probe's own evidence; a later delivery in the same run can only add a code whose own window has passed since. A worker time up to one heartbeat interval and the probe's time limit (18 seconds with the defaults) ahead of the monitor's clock still counts as fresh, and every worker time is copied into the report in ISO form. A fresh worker with historical crashes is healthy once its current checks pass; a build that omits worker status is `not_reported` and cannot clear a worker incident. Deploy this monitor with the new build to observe those fields. None of this enables automatic closes or alert delivery.

`background.cleanup` combines the latest bounded pass with an aggregate read of persisted failures awaiting retry (`lastResult.pendingFailures`) and of files parked for review (`lastResult.parked`). A failed file waiting in backoff, leased for retry or left across a process restart keeps cleanup failed until that file is actually cleared; an empty due poll or another file's successful removal cannot clear its incident. An ordinary first-attempt lease has no persisted failure and does not falsely alert. If the aggregate read fails, the check has no successful result. Empty polls with no recorded failures count as success, but ordinary pending work can still remain. Use the operator cleanup command for full depth/age evidence; do not interpret monitor recovery as proof every queued file was deleted. The monitor copies only allowlisted states, timestamps and aggregate counts into reports and alert messages.

**Resolving a parked export file.** The cleanup worker deletes a swept export's stored file only if the file's metadata names that export and lender, with a numeric generation and, for a ready export, the recorded checksum. A file that fails that check is not the file the export recorded, and no retry changes that, so the worker parks it with its reason and never attempts it again by itself: `ownership_mismatch` (its metadata names another export or lender, or none), `generation_invalid` (its metadata carries no numeric generation, so no delete can be confined to the file that was checked), `artifact_metadata_invalid` (its recorded artifact metadata cannot be read) or `checksum_mismatch` (its recorded checksum is not the export's). The log has `workspace.sweep_file_left` with `parked: true`, and the monitor raises `background_cleanup_needs_review` on every instance until the file is resolved. Storage failures, time limits and the delete's generation race are not parked: they stay `background_cleanup_failed` and are retried with backoff. To resolve a parked file:

1. Run `pnpm run check:export-cleanup` with the service's `DATABASE_URL`. `parkedFiles.files` lists the 20 longest parked files, each with its export ID, lender ID, reason, attempts and since when; `parkedFiles.total` counts them all, and `parkedFiles.cutShort` is true when the list stops short, so resolve these and run the command again for the rest.
2. Read the file's bucket, object name and checksum from the queue, which keeps them out of the command's output and the log, with the service's connection in a read-only session: `SELECT bucket, object_name, checksum FROM valopay_export_cleanup WHERE id = '<export ID>'`.
3. Inspect that object's metadata in App Storage: `valopayExportId`, `valopayMerchantId`, the checksum inside `valopayArtifact` and its generation, against the export ID, lender ID and checksum in the queue.
4. If the object has no ownership metadata at all, only `cacheControl`, it was written before 19 September 2026, when exports did not yet record their owner on the file, and it is parked as `ownership_mismatch`. Its name is the queue's `object_name`, the export's own path, ending `/exports/<lender ID>/<export ID>.<format>`. Download it and compare its SHA-256 with the queue's `checksum`, which the export recorded from the same bytes when it wrote them. If they match, the file is this export's: delete it by hand, then release the tombstone with a reason saying what you compared. If they differ, or the queue has no checksum, treat it as in step 5.
5. If the object is not this export's, because its metadata names another export or lender or its checksum differs, it may be another export's file or evidence of a change: leave it in storage, note it for the historical inventory review of orphaned files (`docs/deployment.md`), and release the tombstone with what you found, `pnpm run check:export-cleanup -- --release <export ID> --reason "<what you found>"`. Nothing is deleted from storage. The command writes the release, with the reason, to this command's log output as `workspace.sweep_file_released`, not to the service's log, so keep that output with your review; it refuses a release where `LOG_LEVEL` would filter that warning line out.
6. If what made the file fail its check was put right after review, for example its metadata was restored or it was removed by hand, re-queue it: `pnpm run check:export-cleanup -- --requeue <export ID>`. The next pass, the service worker's within a minute or `--retry`, attempts it under the same check: a file that now matches, or is gone, is removed, and one that still does not is parked again.

Never delete by hand an object whose metadata names another export or lender. Releasing and re-queueing need only the database. `--retry` also reaches private storage, so before it claims a file it obtains the storage credentials, as every storage request does, and it is refused, with no file claimed, where `PRIVATE_OBJECT_DIR` is not set or those credentials cannot be obtained within 5 seconds: a retry that cannot reach storage would push every due file into backoff. A monitor from before files were parked reads a parked file as `background_cleanup_failed`, since this build keeps cleanup failed while any file is parked; this monitor reads a build that does not count parked files as before.

`scripts/monitor-valopay.mjs` checks liveness, database readiness and the required schema, with bounded requests and no redirects. A missing performance index is a visible `schema_indexes_missing` warning; missing required schema is `schema_unready`. If automatic closes are explicitly expected, it also checks the scheduler state and fresh successful heartbeat, which the API's background worker thread reports to the health answer; a thread that crashed reads as a failed check (`scheduler_failed`) until the restarted thread's first pass succeeds. A completed pass can still contain failed lender closes, so each pass ends by reading from the database what is still owed, and the health answer reports it as counts that name no lender (`scheduler.backlog`, `docs/observability.md`): the monitor reports `scheduler_close_failed` while any lender has a failed scheduled attempt at its pending time, and `scheduler_closes_overdue` while any lender's close is more than 30 minutes past its time, whatever the reason (failing, held, left by a pass whose budget ran out, or catching up missed business dates). Each stays until those lenders' own closes succeed, or their schedules are changed in Settings, even when the process heartbeat is fresh: another lender's close or a quiet pass does not end it, nor does a restart of the API, whose first pass reads the database again (before that pass a process younger than its first pass could be, its first-look delay of five seconds, one interval and a margin, gives the warning `scheduler_backlog_pending`, and an older one `scheduler_stale`; a single restart neither ends nor repeats an open incident, and restarts that keep repeating are raised, as described below). Neither code counts public anonymous sandboxes, the synthetic lenders a visitor's sandbox is seeded with or creates, since a visitor's own data can make their closes fail: the health answer counts them apart (`publicSandboxes`), and the monitor gives them as the warnings `scheduler_public_sandbox_close_failed` and `scheduler_public_sandbox_closes_overdue`, never as an incident. A signed-in person's lenders and a staff pilot's are never counted as sandboxes. The counts are an aggregate, not an inventory: the lenders' consoles (`close_missed`) and the log's failure lines name them. A build from before these counts reports only its last pass with work, which a later pass with work replaces: the monitor then reads that pass's failures and warns `scheduler_backlog_not_reported`. After a period with the scheduler off, lenders owed missed business dates count as overdue until each has caught up, one business date a pass. An intentionally disabled scheduler is healthy unless the operator configures that expectation. On a host whose closes run from a scheduled job it checks instead that the web instances report the scheduler as `external` (`scheduler_not_external` otherwise), since `off` would hide a close the job has missed. Those instances run no pass, but each reads what is still owed every minute, the read a pass ends with, and reports it the same way (`scheduler.backlog`, with `intervalMs` saying how often): the monitor applies the same codes and warnings to it, so a job that has stopped running shows as `scheduler_closes_overdue` once a lender's close it should have run is 30 minutes past its time (a host where only public anonymous sandboxes have automatic closes on gets only the warning `scheduler_public_sandbox_closes_overdue`), and a read missing or older than three intervals is `scheduler_stale`, the code a stale heartbeat raises, since it means the same: the process's own evidence is not fresh. The report labels this evidence `mode_and_fresh_backlog`. A missing read is `scheduler_stale` only from an instance up long enough to have made its first read, 80 seconds at the deployed interval: a younger one, such as an instance the probe itself starts on Autoscale when none is running, gives the warning `scheduler_backlog_pending`, with evidence `first_read_pending` and `closeBacklog` `pending`, as in `on` mode before a process's first pass. That warning blocks commissioning (above), and by itself is no evidence either way for incidents: it neither ends nor repeats one. But no process stays that young: the probe says how long one can be, as `firstReadWithinMs` and in `startupWindowsMs` (the monitor assumes two minutes for a probe that does not say), and the monitor's state keeps when a run of probes that found nothing but startup warnings began (`pendingSince`), with the warnings it has shown (above). A run longer than that means each probe is meeting a new process, one restarting before its first read or an instance the probe itself starts, in either mode, so from then on each such probe counts as `scheduler_stale`, with the run kept beside it (`startupRun`, above) so the alert can be told from an old read, and two in a row open an incident. A monitor whose every probe starts an instance is therefore blind to the backlog, and raises `scheduler_stale` to say so: probe often enough to keep an instance running. The same holds for the background worker, whatever the scheduler setting, `off` included: an instance a probe starts has its worker starting and its first cleanup check pending, so on Autoscale with cleanup on, probes that each start an instance open a worker incident once a run of such probes has outlasted those warnings' windows, 45 and 195 seconds: `background_cleanup_stale`, with `background_stale` when a probe caught a worker before its first heartbeat. Probes that far apart pass both windows by the second probe, so the codes usually arrive together. The job's own runs are still not visible to the monitor. Against a build from before this read, which reports no backlog in external mode, the monitor sees the mode alone (`mode_only`) and warns `scheduler_backlog_not_reported`, which blocks commissioning.

Run `pnpm run check:operations` with `VALOPAY_MONITOR_ORIGIN` set to the HTTPS service origin. The default is a dry run: it prints only the service origin, check time, fixed failure/warning codes, allowlisted observation states and, with a startup warning, the windows above (`startupWindowsMs`, with `firstReadWithinMs` or `backgroundReadWithinMs`) and the worker that answered (`answeredBy`). It reads no customer records and sends no alerts. `--deliver` enables incident and recovery delivery; `--deliver --test-alert` requests a single labelled commissioning message. A `--` before the options is skipped, since pnpm passes one on to the script where npm would not. A test flag without the delivery flag, repeated options and unknown options are refused. A mistyped option is named in the error with the usage; a word that is not an option is only counted, in case it is a credential. Without `VALOPAY_MONITOR_ORIGIN` it says that setting is missing. Other configuration/provider errors do not print setting values or response bodies.

External delivery requires a configured service. The email recipient is the address in `VALOPAY_ALERT_TO`; no address is written into the source. The optional Resend adapter follows the [send-email API](https://resend.com/docs/api-reference/emails/send-email); a verified sender and a provider key are required. Provider acceptance is not proof that a message reached the inbox. Confirm receipt during the host commissioning exercise.

| Variable | Meaning |
| --- | --- |
| `VALOPAY_MONITOR_ORIGIN` | HTTPS origin only; no embedded credentials, path, query or fragment. |
| `VALOPAY_MONITOR_EXPECT_SCHEDULER` | `on` when this host's API process is expected to run automatic closes (a Reserved VM): the scheduler must be running with a fresh successful check, and no lender's close failing or overdue. `external` when a Scheduled Deployment runs them (`VALOPAY_CLOSE_SCHEDULER=external`, `docs/deployment.md`): the web instances must report `external` with a fresh read of what is still owed, and no lender's close failing or overdue. Either in any case; leave it unset to check neither. Any other value stops the monitor with a message naming this setting, never its value. |
| `VALOPAY_MONITOR_OWNER` | Person or operational team responsible for responding. |
| `VALOPAY_MONITOR_STATE_FILE` | Private, persistent state file owned by the monitor; use one process and a lock in the host scheduler. |
| `VALOPAY_MONITOR_ALERT_URL` | Optional HTTPS receiver; this takes precedence over the email adapter. Store any receiver token securely. |
| `VALOPAY_ALERT_RESEND_KEY` | Optional email-provider key, supplied through the host's secret configuration. |
| `VALOPAY_ALERT_FROM` | Verified sender email address for the email adapter. |
| `VALOPAY_ALERT_TO` | Recipient email address for the email adapter; required with the provider key and sender. |

To enable delivery after configuration, run `pnpm run check:operations --deliver`. Use an external scheduler so an unavailable app cannot also stop its own monitor. Two consecutive identical failing probes open an incident. Unchanged incidents stay quiet. A healthy probe after a delivered incident sends a recovery. Failed delivery does not mark an incident as delivered. The state file must be durable; separate instances must not run concurrently against the same file. A crash between receiver acceptance and saving local state can repeat a notification, so receiver-side deduplication remains useful.

To verify the delivery path after it has been configured, run `pnpm run check:operations --deliver --test-alert`. This sends a message explicitly labelled as a test, regardless of current health, and does not create a fake incident, wait for the incident threshold, or read/write incident history. The receiver, owner and email sender/key where relevant are required; an incident-state file is not required for this one message. Success means `accepted_by_receiver` with `recipientReceipt: unverified`. Record the recipient's actual receipt and acknowledgement separately; a successful provider HTTP response is not proof of delivery or of a staffed response. Failure is reported without provider response bodies or credentials, and does not change incident state. No test message is sent by ordinary dry runs or commissioning reports.

The local test starts an actual HTTP receiver, exercises incident delivery, failed delivery, retry, recovery and a labelled test message, and checks email formatting with an injected transport. It also starts the monitor through a symlinked path, which must probe as the real path does. It sends nothing to the selected email address. It runs in CI as `node scripts/monitor-valopay.test.mjs`. `scripts/operator-commands.test.mjs`, run by `pnpm run test:pure`, runs the command itself offline: a dry run against a closed loopback port, `--deliver` after a `--` stopping at the missing receiver, and a mistyped option.

On 18 September 2026 the Replit configuration check found no outbound email service, separate staging Clerk app or secret-manager key provider. The recipient is selected; external delivery and its schedule remain uncommissioned. Readiness monitoring does not replace log-based error-rate alerts, availability measurement or incident ownership drills.

## Measured synthetic recovery

`artifacts/api-server/tests/recovery-rehearsal.integration.test.ts` runs only with both `VALOPAY_RUN_INTEGRATION=1` and `VALOPAY_RUN_RECOVERY=1`, against the local disposable CI database named `valopay`. Under CI a missing opt-in fails the step instead of skipping it, so the rehearsal can never pass there without measuring anything. It creates distinct, uniquely named source and empty restore databases, seeds two synthetic lenders and performs a real PostgreSQL custom-format dump and restore. Credentials are passed to the PostgreSQL tools through environment variables, never command arguments or evidence output.

It compares every row in all eleven application/service tables, including lender-specific access grants, pending/completed recovery requests, teams, active/revoked memberships, invitation hashes and access events, alongside lender settings, outstanding amounts, allocations, close snapshots, idempotency responses and audit chains. The service-only `valopay_export_cleanup` queue includes orphan deletion records whose lender and export have already been removed; their storage identity, checksum, retry history, backoff and in-flight lease must survive unchanged. This queue belongs in the full database backup, not the restricted tenant runtime schema. Two actual synthetic close exports are backed up with their private ownership metadata and restored to an empty local object directory. Their checksums, lengths, lender identities and database export pointers must agree. Missing or corrupted objects fail verification. Cleanup is restricted to the databases and temporary files created by that run.

The rehearsal also restores encrypted import CSV, recovery request/receipt and idempotency response envelopes. A separate test-only wrapping-key vault is restored after the source key material is cleared from memory. Missing keys, incorrect key material and the wrong lender scope must fail closed. The application runtime has no fixture-vault switch: actual deployments use managed KMS wrapping. A real key-recovery drill restores access to retained KMS key versions and their IAM policy; it must never export a managed master key into a database backup.

`src/lib/recovery-manifest.ts` joins the database snapshot checksum, complete private object inventory and reviewed configuration into a strict manifest. The configuration contains only schema version, runtime database role, issuer, allowed origins, retained key identifiers and closed execution gates. It rejects credentials and unknown fields. Before starting a restored environment, compare measured bytes and ownership metadata against an independently protected manifest and compare its configuration against an independently reviewed target configuration. A manifest stored beside a writable backup is not an independent integrity authority; store its hash or signature in a separately controlled recovery record.

CI retains the report for 14 days, and fails the job if it is missing. It includes the outcome (`passed`), snapshot time, database and complete-package backup/restore durations, row counts, restored object count and verification scope, with no database URLs, secret keys, record payloads or customer identifiers. A rehearsal that fails writes a report too, saying only `failed` and after how long, never the error, which could quote a synthetic record; CI runs the rehearsal even when a database suite before it failed. One synthetic write is deliberately made after the snapshot and is absent after restore; the report records this observed data loss and the age of the recovered snapshot. `VALOPAY_REHEARSAL_REPORT` selects its output path. This proves complete logical recovery across the local database/object/key fixtures. It does not prove production point-in-time recovery, hosted App Storage ACL restoration, managed KMS custody, real identity-service configuration or an agreed recovery-time/data-loss target. Those require a separate host rehearsal before real data is admitted.

## Staff access on the restricted runtime

A separate staging app and store once rehearsed this path on a synthetic protected note, apart from the application. They have been removed: the application's own staff access and the optional restricted runtime (`docs/pilot-operations-controls.md`, `docs/pilot-database.md`) carry the path, and its checks run against them. In staff mode each request reloads the person's membership of the organisation and requires an active verified Clerk session and both authentication factors, fresh ones for any change. The browser cannot choose a role, workspace or principal, and a change must come from an origin in `VALOPAY_STAFF_ORIGINS`.

`artifacts/api-server/tests/pilot-workflow.integration.test.ts` and `artifacts/api-server/tests/staff-lender-access.integration.test.ts` run the real routes and repository on PostgreSQL: no session is a 401; stale MFA, a replay with stale MFA and a revoked membership are refused; a removed grant, another workspace's lender and another lender's record named through this lender's address are not found; a replayed request returns its first answer, and a stale edit is refused with a 409. `artifacts/api-server/tests/runtime-isolation.integration.test.ts` runs the repository under the actual restricted login, and `artifacts/api-server/tests/api-security.test.ts` checks the origin rule. Raw import rows are sealed at rest as `docs/pilot-operations-controls.md` describes. Verified-session fixtures replace the external identity service only inside the tests; the application uses [Clerk middleware](https://clerk.com/docs/reference/express/clerk-middleware), and no test claims to verify an unconfigured Clerk deployment.

Before commissioning, provision a separate Clerk app, the restricted database login and schema, a service member, a private key provider and the approved origin. Full pilot workflows, action-bound reverification, key lifecycle, deployment rollback and independent assessment remain part of pilot acceptance.
