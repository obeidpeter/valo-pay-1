# Operational rehearsals

The shipped sandbox remains synthetic. These checks exercise recovery, alert delivery and staff access on the restricted runtime without changing the deployed database, enabling the scheduler or sending collection instructions.

## Commissioning evidence before activation

Run `node scripts/commission-operations.mjs` with the same monitor settings described below. Set `VALOPAY_OPERATIONS_HOST_MODE` to `reserved-vm`, `autoscale` or `other`, reflecting the deployment configuration you have checked, and set `VALOPAY_MONITOR_EXPECT_SCHEDULER` to the intended `on` or `external` mode. The command makes only the public liveness and readiness requests. It does not create a workspace, run a close, send an alert or change configuration. `VALOPAY_OPERATIONS_REPORT` optionally writes the JSON report to a private operator path; the file is replaced atomically and created with owner-only permissions on systems that enforce them. Keep that directory outside the public source and restrict its Windows access permissions where applicable.

The report separates three kinds of evidence:

- **Configuration:** whether required delivery settings and an incident-state path exist and have valid syntax. Setting presence does not prove the provider key, sender or persistent storage works. The host mode is the operator's declared setting, not a remote hosting inspection.
- **Observations:** the liveness, database, required schema and scheduler state that this HTTP probe saw. A successful process heartbeat is distinguishable from an external scheduler's mode-only answer. An in-process scheduler on an Autoscale host is flagged because it stops when the host scales down. With `on`, `closeBacklog` gives the number of lenders whose close is failing or overdue, as the scheduler's latest pass read them from the database, without naming any; either above zero is a blocker, and so is a build that does not report them (`scheduler_backlog_not_reported`), since it shows a failed close only until a later pass with work. Public anonymous sandboxes' own counts are beside them, as `publicSandboxes`, and their warnings are never blockers.
- **Acceptance still needed:** an independently scheduled monitor with durable state; receipt and acknowledgement of a test alert; a measured isolated recovery of hosted database, private objects and required key access; and a close failure/recovery rehearsal. An external close job additionally needs actual completion evidence and a missed-run alarm. Reporting `external` alone does not establish either.

Exit status 2 means the completed check found a configuration or observed service problem; 1 means it could not produce a usable report. Exit status 0 means only that the configured settings and observations passed: the report still says `observations_passed_acceptance_required`, never that unattended pilot operation has been accepted. The script records no receiver URL, email address, key, private state path or customer record. `node scripts/commission-operations.test.mjs` checks the report and the actual command offline, including failures and the distinction between configuration and acceptance.

## Incident and recovery delivery

`scripts/monitor-valopay.mjs` checks liveness, database readiness and the required schema, with bounded requests and no redirects. A missing performance index is a visible `schema_indexes_missing` warning; missing required schema is `schema_unready`. If automatic closes are explicitly expected, it also checks the scheduler state and fresh successful heartbeat, which the API's background worker thread reports to the health answer; a thread that crashed reads as a failed check (`scheduler_failed`) until the restarted thread's first pass succeeds. A completed pass can still contain failed lender closes, so each pass ends by reading from the database what is still owed, and the health answer reports it as counts that name no lender (`scheduler.backlog`, `docs/observability.md`): the monitor reports `scheduler_close_failed` while any lender has a failed scheduled attempt at its pending time, and `scheduler_closes_overdue` while any lender's close is more than 30 minutes past its time, whatever the reason (failing, held, left by a pass whose budget ran out, or catching up missed business dates). Each stays until those lenders' own closes succeed, or their schedules are changed in Settings, even when the process heartbeat is fresh: another lender's close or a quiet pass does not end it, nor does a restart of the API, whose first pass reads the database again (before that pass the monitor reports `scheduler_stale`, which neither ends nor repeats an open incident). Neither code counts public anonymous sandboxes, the synthetic lenders a visitor's sandbox is seeded with or creates, since a visitor's own data can make their closes fail: the health answer counts them apart (`publicSandboxes`), and the monitor gives them as the warnings `scheduler_public_sandbox_close_failed` and `scheduler_public_sandbox_closes_overdue`, never as an incident. A signed-in person's lenders and a staff pilot's are never counted as sandboxes. The counts are an aggregate, not an inventory: the lenders' consoles (`close_missed`) and the log's failure lines name them. A build from before these counts reports only its last pass with work, which a later pass with work replaces: the monitor then reads that pass's failures and warns `scheduler_backlog_not_reported`. After a period with the scheduler off, lenders owed missed business dates count as overdue until each has caught up, one business date a pass. An intentionally disabled scheduler is healthy unless the operator configures that expectation. On a host whose closes run from a scheduled job it checks instead that the web instances report the scheduler as `external` (`scheduler_not_external` otherwise), since `off` would hide a close the job has missed; the job's own runs are not visible to it, and the report explicitly labels this evidence `mode_only`.

Run `pnpm run check:operations` with `VALOPAY_MONITOR_ORIGIN` set to the HTTPS service origin. The default is a dry run: it prints only the service origin, check time, fixed failure/warning codes and allowlisted observation states. It reads no customer records and sends no alerts. `--deliver` enables incident and recovery delivery; `--deliver --test-alert` requests a single labelled commissioning message. A `--` before the options is skipped, since pnpm passes one on to the script where npm would not. A test flag without the delivery flag, repeated options and unknown options are refused. A mistyped option is named in the error with the usage; a word that is not an option is only counted, in case it is a credential. Without `VALOPAY_MONITOR_ORIGIN` it says that setting is missing. Other configuration/provider errors do not print setting values or response bodies.

External delivery requires a configured service. The email recipient is the address in `VALOPAY_ALERT_TO`; no address is written into the source. The optional Resend adapter follows the [send-email API](https://resend.com/docs/api-reference/emails/send-email); a verified sender and a provider key are required. Provider acceptance is not proof that a message reached the inbox. Confirm receipt during the host commissioning exercise.

| Variable | Meaning |
| --- | --- |
| `VALOPAY_MONITOR_ORIGIN` | HTTPS origin only; no embedded credentials, path, query or fragment. |
| `VALOPAY_MONITOR_EXPECT_SCHEDULER` | `on` when this host's API process is expected to run automatic closes (a Reserved VM): the scheduler must be running with a fresh successful check, and no lender's close failing or overdue. `external` when a Scheduled Deployment runs them (`VALOPAY_CLOSE_SCHEDULER=external`, `docs/deployment.md`): the web instances must report `external`. Either in any case; leave it unset to check neither. Any other value stops the monitor with a message naming this setting, never its value. |
| `VALOPAY_MONITOR_OWNER` | Person or operational team responsible for responding. |
| `VALOPAY_MONITOR_STATE_FILE` | Private, persistent state file owned by the monitor; use one process and a lock in the host scheduler. |
| `VALOPAY_MONITOR_ALERT_URL` | Optional HTTPS receiver; this takes precedence over the email adapter. Store any receiver token securely. |
| `VALOPAY_ALERT_RESEND_KEY` | Optional email-provider key, supplied through the host's secret configuration. |
| `VALOPAY_ALERT_FROM` | Verified sender email address for the email adapter. |
| `VALOPAY_ALERT_TO` | Recipient email address for the email adapter; required with the provider key and sender. |

To enable delivery after configuration, run `pnpm run check:operations --deliver`. Use an external scheduler so an unavailable app cannot also stop its own monitor. Two consecutive identical failing probes open an incident. Unchanged incidents stay quiet. A healthy probe after a delivered incident sends a recovery. Failed delivery does not mark an incident as delivered. The state file must be durable; separate instances must not run concurrently against the same file. A crash between receiver acceptance and saving local state can repeat a notification, so receiver-side deduplication remains useful.

To verify the delivery path after it has been configured, run `pnpm run check:operations --deliver --test-alert`. This sends a message explicitly labelled as a test, regardless of current health, and does not create a fake incident, wait for the incident threshold, or read/write incident history. The receiver, owner and email sender/key where relevant are required; an incident-state file is not required for this one message. Success means `accepted_by_receiver` with `recipientReceipt: unverified`. Record the recipient's actual receipt and acknowledgement separately; a successful provider HTTP response is not proof of delivery or of a staffed response. Failure is reported without provider response bodies or credentials, and does not change incident state. No test message is sent by ordinary dry runs or commissioning reports.

The local test starts an actual HTTP receiver, exercises incident delivery, failed delivery, retry, recovery and a labelled test message, and checks email formatting with an injected transport. It sends nothing to the selected email address. It runs in CI as `node scripts/monitor-valopay.test.mjs`. `scripts/operator-commands.test.mjs`, run by `pnpm run test:pure`, runs the command itself offline: a dry run against a closed loopback port, `--deliver` after a `--` stopping at the missing receiver, and a mistyped option.

On 18 September 2026 the Replit configuration check found no outbound email service, separate staging Clerk app or secret-manager key provider. The recipient is selected; external delivery and its schedule remain uncommissioned. Readiness monitoring does not replace log-based error-rate alerts, availability measurement or incident ownership drills.

## Measured synthetic recovery

`artifacts/api-server/tests/recovery-rehearsal.integration.test.ts` runs only with both `VALOPAY_RUN_INTEGRATION=1` and `VALOPAY_RUN_RECOVERY=1`, against the local disposable CI database named `valopay`. Under CI a missing opt-in fails the step instead of skipping it, so the rehearsal can never pass there without measuring anything. It creates distinct, uniquely named source and empty restore databases, seeds two synthetic lenders and performs a real PostgreSQL custom-format dump and restore. Credentials are passed to the PostgreSQL tools through environment variables, never command arguments or evidence output.

It compares every row in all ten application tables, including lender-specific access grants, pending/completed recovery requests, teams, active/revoked memberships, invitation hashes and access events, alongside lender settings, outstanding amounts, allocations, close snapshots, idempotency responses and audit chains. Two actual synthetic close exports are backed up with their private ownership metadata and restored to an empty local object directory. Their checksums, lengths, lender identities and database export pointers must agree. Missing or corrupted objects fail verification. Cleanup is restricted to the databases and temporary files created by that run.

The rehearsal also restores encrypted import CSV, recovery request/receipt and idempotency response envelopes. A separate test-only wrapping-key vault is restored after the source key material is cleared from memory. Missing keys, incorrect key material and the wrong lender scope must fail closed. The application runtime has no fixture-vault switch: actual deployments use managed KMS wrapping. A real key-recovery drill restores access to retained KMS key versions and their IAM policy; it must never export a managed master key into a database backup.

`src/lib/recovery-manifest.ts` joins the database snapshot checksum, complete private object inventory and reviewed configuration into a strict manifest. The configuration contains only schema version, runtime database role, issuer, allowed origins, retained key identifiers and closed execution gates. It rejects credentials and unknown fields. Before starting a restored environment, compare measured bytes and ownership metadata against an independently protected manifest and compare its configuration against an independently reviewed target configuration. A manifest stored beside a writable backup is not an independent integrity authority; store its hash or signature in a separately controlled recovery record.

CI retains the report for 14 days, and fails the job if it is missing. It includes the outcome (`passed`), snapshot time, database and complete-package backup/restore durations, row counts, restored object count and verification scope, with no database URLs, secret keys, record payloads or customer identifiers. A rehearsal that fails writes a report too, saying only `failed` and after how long, never the error, which could quote a synthetic record; CI runs the rehearsal even when a database suite before it failed. One synthetic write is deliberately made after the snapshot and is absent after restore; the report records this observed data loss and the age of the recovered snapshot. `VALOPAY_REHEARSAL_REPORT` selects its output path. This proves complete logical recovery across the local database/object/key fixtures. It does not prove production point-in-time recovery, hosted App Storage ACL restoration, managed KMS custody, real identity-service configuration or an agreed recovery-time/data-loss target. Those require a separate host rehearsal before real data is admitted.

## Staff access on the restricted runtime

A separate staging app and store once rehearsed this path on a synthetic protected note, apart from the application. They have been removed: the application's own staff access and the optional restricted runtime (`docs/pilot-operations-controls.md`, `docs/pilot-database.md`) carry the path, and its checks run against them. In staff mode each request reloads the person's membership of the organisation and requires an active verified Clerk session and both authentication factors, fresh ones for any change. The browser cannot choose a role, workspace or principal, and a change must come from an origin in `VALOPAY_STAFF_ORIGINS`.

`artifacts/api-server/tests/pilot-workflow.integration.test.ts` and `artifacts/api-server/tests/staff-lender-access.integration.test.ts` run the real routes and repository on PostgreSQL: no session is a 401; stale MFA, a replay with stale MFA and a revoked membership are refused; a removed grant, another workspace's lender and another lender's record named through this lender's address are not found; a replayed request returns its first answer, and a stale edit is refused with a 409. `artifacts/api-server/tests/runtime-isolation.integration.test.ts` runs the repository under the actual restricted login, and `artifacts/api-server/tests/api-security.test.ts` checks the origin rule. Raw import rows are sealed at rest as `docs/pilot-operations-controls.md` describes. Verified-session fixtures replace the external identity service only inside the tests; the application uses [Clerk middleware](https://clerk.com/docs/reference/express/clerk-middleware), and no test claims to verify an unconfigured Clerk deployment.

Before commissioning, provision a separate Clerk app, the restricted database login and schema, a service member, a private key provider and the approved origin. Full pilot workflows, action-bound reverification, key lifecycle, deployment rollback and independent assessment remain part of pilot acceptance.
