The owner chooses the deployment type in Replit's publishing settings; nothing in this repository changes it.

## What is deployed

`.replit` publishes to Replit Autoscale (`deploymentTarget = "autoscale"`). The API's own deployment settings are in `artifacts/api-server/.replit-artifact/artifact.toml`: the build (`pnpm --filter @workspace/api-server run build`, which writes the server, its background worker thread and the one-shot close pass to `artifacts/api-server/dist`), the start command (`node --enable-source-maps artifacts/api-server/dist/index.mjs`), the start-up health check and the environment the deployed process gets:

| Setting | Value | Why |
| --- | --- | --- |
| `NODE_ENV` | `production` | Production behaviour: JSON log lines and the Clerk proxy. |
| `PORT` | `8080` | The port the router sends `/api` to. |
| `VALOPAY_EXPIRED_WORKSPACE_CLEANUP` | `on` | Anonymous sandboxes nobody has changed for 30 days are deleted (below). |
| `CLERK_TELEMETRY_DISABLED` | `1` | The Clerk SDK sends no telemetry and prints no telemetry notice on stdout (below). |

Credentials (`DATABASE_URL`, the Clerk keys, `PRIVATE_OBJECT_DIR` and any optional service keys) come from Replit's secret manager, never from these files. The console is built and served as static files (`artifacts/valo-pay/.replit-artifact/artifact.toml`).

Among the Clerk keys, `CLERK_JWT_KEY` is the instance's JWT public key, pasted in PEM form as Clerk shows it; the start-up check reads it exactly as Clerk does, so the forms Clerk also reads start too (lines joined, spaces for the line breaks, the body alone: the README's environment table lists them). A staff host (`VALOPAY_STAFF_ACCESS=staging`) must have it beside `CLERK_SECRET_KEY`, and any host that sets it must give a value Clerk can use (not one on a single line with `\n` escapes, nor one holding a character Clerk misreads, such as a narrow no-break space): otherwise the process does not start, and its `config.invalid` line names the setting and why. It is optional elsewhere, but without it a forged session token makes the API fetch the instance's keys from Clerk's Backend API with the secret key, and only the per-network request limit bounds those fetches (1,200 a minute from each IPv4 address or IPv6 /64, in each instance). The start-up check cannot tell another instance's key from the right one, so sign in once after setting it.

When the console is built with `VITE_CLERK_PROXY_URL`, its sign-in calls and the Clerk bundle go through the production sign-in proxy (`/api/__clerk`), which keeps its own budgets in each instance (`docs/audit-remediation-2026-09-26.md`): 240 requests a minute and 8 at once from one client network, and 64 at once in the process, so eight networks at their limit fit. Colleagues behind one office address share a network's budget, session refreshes included; for a pilot whose staff share an address, raise `VALOPAY_CLERK_PROXY_RATE`, and `VALOPAY_CLERK_PROXY_NETWORK_CONCURRENCY` if many sign in at once. The process's limit follows at eight times the network's, or `VALOPAY_CLERK_PROXY_CONCURRENCY` sets it higher; the start-up check refuses a value outside its rule (README). Clerk's response headers must arrive within 30 seconds. After them a download, such as the bundle, is cut off once the proxy has handed none of it to the browser's connection for 30 seconds (a reply Clerk sends without its length, once none of it has arrived from Clerk for 30 seconds while the proxy collects it), or after 10 minutes in all. The connection takes more only as the browser acknowledges earlier bytes, and the network's buffers sit in between, so the proxy cannot see bytes reach the browser: a browser taking less than a few KiB a second, roughly 100 to 200 KiB in 30 seconds, may be cut off while bytes still reach it.

## What holds a release back

The deployment's start-up health check is `GET /api/readyz`, not the liveness answer. Readiness makes one bounded round trip to the database and reads its catalogue, so:

- a database that does not answer, or lacks a table or column this build needs (a migration not yet applied) or a unique index or check constraint its schema declares, or still holds a guard this build replaced (the provider event guard migration 009 removes, which an earlier copy of 009 could leave in a runtime schema), answers 503, the health check fails and the new build does not go live;
- a database that lacks only a read index a migration adds answers 200 with `checks.schema.status` `indexes_missing`: every request still works, only slower, so the release goes ahead, and a `readiness.indexes_missing` log line names the index and the migration that adds it.

Apply a build's migrations before publishing it (`docs/database-migrations.md`). The build serving now may not check unique indexes and check constraints (builds from before the 23 September 2026 audit fixes do not), so its readiness cannot show a guard the new build requires: run the guard query in `docs/database-migrations.md` before publishing, or the first publish may be held back. The process also refuses to start when a setting breaks its rule: it writes one `config.invalid` line naming each setting to correct, never its value, and exits with status 1, so the health check never passes (`docs/observability.md`).

## Autoscale and the work the API process does on its own

Two pieces of work run inside the API process rather than as separate jobs, on its background worker thread (below): the scheduled daily close (REC-01, each lender's configured West Africa Time, default 07:00) and the export worker. Replit Autoscale runs instances only while requests arrive and scales an idle deployment down to none, so:

- **Scheduled closes run late.** While no instance runs, nothing ticks. A close due at 07:00 runs at the first tick after the next request starts an instance, about five seconds after it starts, and a close that starts more than 30 minutes after its time is recorded as late; until then the overview shows the `close_missed` alert.
- **Queued exports wait.** An export queued before the deployment went idle starts when the next request starts an instance. One in progress when an instance stops returns to the queue instead of failing.
- **Per-address limits are per instance.** The general request limit, the new-sandbox limit and the Paystack test-delivery limit count in each instance's memory: with several instances a client can make up to that many times as many requests, and the counts start again whenever an instance starts. The per-lender share of database connections is per instance too (`docs/DATABASE_SECURITY.md`).

## The background worker thread

The API process runs the scheduled daily close and the export worker on a worker thread of its own (`artifacts/api-server/src/background.ts`, built as `dist/background.mjs` beside the server), not on the event loop that answers requests. A month-end close or a large export therefore never holds up another tenant's requests or a health probe; a lender's own requests still wait for its close, as they wait for any change to it. A close a person runs through the API stays on the request path, since it answers that request.

- **Its connections.** The thread has its own database pool of three connections: one for the scheduled close, which closes one lender at a time (or, with `VALOPAY_CLOSE_SCHEDULER=external`, reads what is still owed every minute, in turn with the daily audit checks a person's closes ask for), and one for each of the two export slots. With `external`, a read goes ahead of the audit checks still waiting, never ahead of the one in progress, so it waits for that check at most. The requests' pool is `VALOPAY_DATABASE_POOL_SIZE` (10 by default) and readiness keeps one short-lived connection, so an instance holds at most that size plus four, 14 by default. Size the database's connection limit for instances × (size + 4), plus one for the one-shot close pass where it runs.
- **Its log and state.** Its lines are written through the main thread, with the same events as before and `thread: "background"` added, and the scheduler's state reaches `/api/healthz` and the console by message (`docs/observability.md`). The health answer also reports `background`: enabled jobs, a heartbeat every 10 seconds (stale after 45), process-lifetime crash/restart counts and completed cleanup checks, including successful empty polls. With its default one-minute interval, cleanup is stale after 195 seconds without a completed check. This works when the close scheduler is off and does not depend on retrieving startup logs. Liveness stays 200 while the monitor raises worker failures separately; cleanup check success is not evidence of an empty durable queue or a successful deletion. Deploy the updated monitor with this build and retain the separate operator queue check.
- **A crash.** A thread that fails is logged (`background.crashed`) and started again after a wait that doubles from a second to a minute, back to a second once a thread has run for a minute; the API carries on. A close it was running rolls back with its connection and runs at the new thread's first tick; an export it was running keeps its lease and is recovered when the lease expires, as after a process crash. Until the new thread's first pass succeeds, `/api/healthz` shows the failure in the scheduler's `lastErrorAt` and the console does not advertise the next automatic close.
- **Shutdown.** On SIGTERM or SIGINT the process stops the thread before it exits: no close or export starts, the lender close in progress finishes, the exports in progress return to the queue and the thread ends its pool (`background.stopped`). The process's 10 s deadline still bounds it all: a close unfinished by then rolls back with its connection and runs again after restart, and an export not yet returned keeps its lease.

Close times are not staggered. Every lender on the default 07:00 closes then, one after another; on the worker thread a morning of closes delays no request and no health probe, so spreading the times would gain nothing and would move lenders' closes from the time they chose.

## Running scheduled closes on time

Choose one of these for any host whose lenders rely on the automatic close.

Before changing this setting, capture `node scripts/commission-operations.mjs` with the intended scheduler mode and actual hosting type (`docs/operational-rehearsals.md`). A healthy API with `VALOPAY_CLOSE_SCHEDULER=off` proves no automatic close. A fresh in-process heartbeat on Autoscale does not prove the process will exist at the next due time. The commissioning report keeps these observations separate from the completed close, alert receipt and isolated recovery evidence required for acceptance.

1. **A Reserved VM.** Change the deployment type from Autoscale to Reserved VM in Replit's publishing settings. The instance stays up, the API's scheduler ticks every minute on its background worker thread and closes run on time. Leave `VALOPAY_CLOSE_SCHEDULER` unset (or `on`). Each pass ends by reading the lenders whose close is failing or overdue, and `/api/healthz` reports them as counts until each of those lenders' closes succeeds, across other lenders' passes and restarts; the monitor raises an incident on them (`docs/operational-rehearsals.md`). Public anonymous sandboxes are counted apart (below). A Reserved VM is billed while it runs: this is the owner's billing decision.
2. **Autoscale with a Scheduled Deployment.** Keep the Autoscale deployment and set `VALOPAY_CLOSE_SCHEDULER=external` in its environment, so its instances never run the scheduler but still read and report the closes the job owes, a missed one included (below). Then create a Replit Scheduled Deployment of this repository that runs the one-shot close pass:
   - build command: `pnpm --filter @workspace/api-server run build`;
   - run command: `node --enable-source-maps artifacts/api-server/dist/close-pass.mjs`;
   - schedule: every 15 minutes (cron `*/15 * * * *`), so a close starts well within the 30 minutes after which it is recorded as late;
   - environment: the same `DATABASE_URL` secret as the web deployment and the same database settings (`VALOPAY_DATABASE_POOL_SIZE`, and `VALOPAY_RUNTIME_ISOLATION` with its companions where the restricted runtime is on), with `NODE_ENV=production`. It needs no port, no Clerk key and no storage.

The one-shot close pass (`artifacts/api-server/src/close-pass.ts`, run locally with `pnpm --filter @workspace/api-server run close-pass` after a build) is the scheduler's own pass run once: the same due-lender reads, the same fair order, one lender per system transaction through the scoped repository, the same failure backoff and audit, and the same daily check of a lender's whole audit chain after its first close of the day, run once the pass's closes are done (README, Scheduled daily close), with a budget of ten minutes instead of 45 seconds: after ten minutes it starts no further close or check and finishes the one in progress, and a lender whose check it did not reach is checked after its next close. It does not act on `VALOPAY_CLOSE_SCHEDULER`, which is the web server's switch, but checks it at start-up as the server does: a value the server would refuse stops the pass with a `config.invalid` line and exit status 1 before it closes anything, so give it the web deployment's value or leave it unset. Another process closing at the same time never closes the same lender twice. A stop signal ends it after the lender close in progress. It ends with one `close.one_shot` line and its exit status:

| Exit status | Meaning |
| --- | --- |
| 0 | The pass took up every lender that was due and none of their closes failed: each was closed, paused (an idle sandbox) or left to another process that held it or had just closed it; and, as the pass read the database at its end, no lender's close is failing or more than 30 minutes past its time. Public anonymous sandboxes are counted apart (below): a sandbox's close can have failed, be failing or overdue, or be left due by the budget, after a 0. A lender owed several missed business dates gets one close a run, for the oldest, so it can still be due after a 0 while its next date is less than 30 minutes past. |
| 2 | The pass ran, but at least one lender's close failed, its ten-minute budget ran out with a lender still due, or a lender's close is still failing or overdue from an earlier run. A failure is recorded with its next attempt (2, 4, 8, 16, 32 minutes, then hourly) and a later run retries it; the lender's log line has the error. Until that lender's close succeeds, every run fails, whether or not it tried the lender, so the history shows it for as long as it lasts; the same holds for a close more than 30 minutes past its time, such as one a request held or one of several missed business dates still being caught up. The lenders the budget left are still due, and the next run takes them up. The `close.one_shot` line says which: `failed` above 0, `budgetSpent` true, `failing` or `overdue` above 0, or several. None of these counts public anonymous sandboxes, whose own failed, failing and overdue closes the line gives as `publicSandboxes` and which never make it 2. The pass takes sandboxes up last, so when its budget runs out one read of the next due lender says whether only sandboxes are left: the line then says `budgetSpent` false and `publicSandboxes.budgetSpent` true. |
| 1 | The pass could not run (a setting refused at start-up, the database unavailable) or was stopped before it finished, whatever else it did. The lenders it did not reach are still due for the next run. |

The failing and overdue counts cover every lender whose automatic close is on except public anonymous sandboxes: the synthetic lenders a visitor's sandbox is seeded with or creates. A signed-in person's lenders and a staff pilot's never count as such. A sandbox created by a build older than commit 310e159 of 17 September 2026, which began flagging sandboxes, carries no `anonymousWorkspace` flag, so its lenders count as lenders and neither the idle pause nor the expiry sweep (below) touches it: an operator finds such lenders with `SELECT id, workspace_id FROM valopay_merchants WHERE NOT (settings ? 'anonymousWorkspace')`, which also lists any lender a signed-in person created with such a build. A visitor's own synthetic data can make its sandbox's close fail, such as amounts beyond the supported range, which the close refuses, so the sandboxes are counted apart, in `scheduler.backlog.publicSandboxes` on `/api/healthz` and in `publicSandboxes` on the `close.run` and `close.one_shot` lines. A sandbox stays counted there until its close succeeds, its schedule changes or, seven days after anyone last changed it, the scheduler pauses its automatic close as idle. The monitor gives their failing and overdue closes as warnings (`scheduler_public_sandbox_close_failed`, `scheduler_public_sandbox_closes_overdue`), never as an incident or a commissioning blocker, and they never make a one-shot run exit 2. The sandbox's `scheduled daily close failed` log line names it, with the error and `publicSandbox: true`.

A failed run shows as failed in the Scheduled Deployment's history. On a host run this way the web instances report the scheduler as `external` on `/api/healthz` and the console says "Daily closes run from a scheduled job.", without advertising a next run, since the web instances cannot see the job's. They still judge each lender's schedule as a running service would: a close the job has not run 30 minutes after its time is missed, so the overview raises the `close_missed` alert naming the business dates still owed and the console asks for a daily close and a check of the job. Each web instance also reads, every minute on its background worker thread, what the scheduler's own pass would read at its end: how many lenders' closes are failing or more than 30 minutes past their time, public anonymous sandboxes apart. `/api/healthz` reports the latest read as `scheduler.backlog`, with its `checkedAt`, and `scheduler.intervalMs` says how often it reads; a read that fails is logged (`close.backlog_failed`) and keeps the last one, whose `checkedAt` ages. So if the Scheduled Deployment stops, or fails at every run (a rotated secret, a refused setting), its closes become overdue: the lenders' consoles say so, and so does every web instance's health answer. `VALOPAY_CLOSE_SCHEDULER=off` would hide all of this, which suits only a host where nobody runs automatic closes. The closes the pass records are scheduled closes, shown as such in Reports. Set `VALOPAY_MONITOR_EXPECT_SCHEDULER=external` for such a host (`docs/operational-rehearsals.md`): the monitor then checks that the web instances report `external` and applies the same codes to what they read as on a host that runs its own closes, so a job that has stopped running raises `scheduler_closes_overdue` once a lender's close it should have run is 30 minutes past its time (a host where only public anonymous sandboxes have automatic closes on gets only the warning `scheduler_public_sandbox_closes_overdue`), and a read older than three minutes raises `scheduler_stale`, as does a missing one from an instance up long enough to have made its first read: its first-read delay of five seconds, one interval and a margin, 80 seconds in all. An instance younger than that, such as one the probe itself starts on Autoscale when none is running, has not read yet: the monitor gives the warning `scheduler_backlog_pending` instead, which blocks commissioning until the check is run again once the instance has been up for about a minute and a half, and by itself neither ends nor repeats an incident. No instance stays that young, so once the monitor's probes have found nothing but that warning for longer than 80 seconds, it is meeting a new instance at each probe, one restarting before its first read or one the probe itself starts, and each such probe counts as `scheduler_stale`, with the run beside it (`startupRun`, `docs/operational-rehearsals.md`): two in a row open an incident. A monitor whose every probe starts an instance is therefore blind to the backlog, and says so with `scheduler_stale`: probe often enough to keep an instance running. That advice covers the background worker too, on any Autoscale host with cleanup on, whether the scheduler is `external` or `off`: an instance a probe starts has its worker starting and its first cleanup check pending (`background_starting`, `background_cleanup_pending`), so probes that each start an instance open a worker incident once a run of such probes has outlasted those warnings' windows, 45 and 195 seconds: `background_cleanup_stale`, with `background_stale` when a probe caught a worker before its first heartbeat. Probes that far apart pass both windows by the second probe, so the codes usually arrive together. The monitor still cannot see the job's runs; watch those in the Scheduled Deployment's history and its `close.one_shot` lines. Against a build from before this read the monitor sees the mode alone and warns `scheduler_backlog_not_reported`.

Commission the scheduled job on an isolated synthetic host first: record the deployed build, due time and business date; let the job perform the close; confirm one scheduled close and its reviewed evidence; then test an interrupted or failed run and its recovery without duplicate closes. Configure an independent alarm for a missing or failed job execution, and verify that alarm reaches the selected operator: the monitor above, scheduled and delivering, raises a job that has stopped running as overdue closes, and the Scheduled Deployment's history shows a run that failed. Keep run identifiers, expected/observed times and the operator's acknowledgement in the private commissioning record. Do not treat the web process's `external` mode or a successful configuration save as job completion evidence. A machine-readable report explicitly leaves external completion and missed-run detection unverified until that exercise has been observed.

Exports need no schedule of their own: the export worker runs whenever an instance does, so a queued export waits at most until the next request.

## Anonymous sandboxes on the deployed host

The 30-day expiry policy, durable cleanup queue, running-export exclusion and interrupted-upload allowance are deployed. The sweep checks for running exports after locking the workspace and every lender: any running job, including one whose lease expired, retains the whole workspace until it settles or recovers. For a non-ready export with an earlier generation attempt, the first cleanup check waits five minutes after the sweep. This bounded allowance gives interrupted uploads time to settle; it does not prove that an external storage provider can never complete a write arbitrarily late.

The deployment sets `VALOPAY_EXPIRED_WORKSPACE_CLEANUP=on`. An anonymous sandbox becomes eligible for deletion when it is more than 30 days old and nobody has changed it for 30 days (entries by the seed and the scheduled close do not count as changes). Deletion happens only when a new anonymous sandbox is created, that is when a browser without a sandbox cookie first opens the console: that request deletes up to five eligible sandboxes, oldest first, removing their lenders, records, stored answers and operations journal. A sandbox whose lender a scheduled close, the export worker, a test delivery or a request holds at that moment is left for a later sweep. So an eligible sandbox is deleted at the next new visitor's arrival, five at a time, not at the moment it turns 30 days idle; on a quiet host it can stay longer. Once that deletion has committed, the same request removes from private storage the export files the swept sandboxes' lenders wrote there, each only if its metadata names that export and lender (a file an approved retention run removed is not touched again); it starts no removal after five seconds, so the new visitor is not held for long. The sweep first writes private-file tombstones to `valopay_export_cleanup` in the same transaction. A storage failure never undoes the deletion or loses the remaining file identities. The service background worker retries five due files a pass, every minute, with leased claims, bounded database waits and backoff from 30 seconds to one hour. It releases database connections before storage calls and shares the existing three-connection background pool. A crash leaves a two-minute lease, after which another worker can continue. Ownership, generation and any recorded checksum must still match. A file whose metadata does not match is not the export it should be, which no retry changes: it is parked for review with its reason and no further automatic attempt, and the monitor raises `background_cleanup_needs_review` until an operator resolves it (`docs/operational-rehearsals.md`); storage failures, time limits and the delete's generation race are retried with backoff as before. The worker runs on service hosts even when creation-time expiry is off, but never inside a restricted tenant runtime. On Autoscale, progress needs a running instance; `pnpm run check:export-cleanup -- --retry` can run one bounded due pass as a service operator, where the service's storage settings and credentials are: without `PRIVATE_OBJECT_DIR`, or without storage credentials it can obtain within 5 seconds, it is refused before any file is claimed, and ends at once even while the storage sidecar never answers. `pnpm run check:export-cleanup` reports aggregate pending, ready, leased, retried, failed (awaiting a retry) and parked counts plus the oldest item, and lists the 20 longest parked files with why and how many are parked in all; `-- --requeue <export ID>` and `-- --release <export ID> --reason "..."` resolve a parked file after review and need only the database. Exit 2 means backlog remains, and exit 1 means the check failed or was refused. Private object paths stay in the queue, not the log. On another host that lacks migration 013, apply it before this build; its presence and privileges were already verified on the deployed sandbox on 27 September 2026. Keep the queue on rollback; do not clear it to hide failures. An earlier build never attempts a parked file either, and counts it among its failed tombstones. Files already orphaned by older builds need separate historical inventory review. Signed-in and staff workspaces are never swept. The development workspace leaves the setting unset, so nothing is deleted there.

## Clerk telemetry

With development-instance keys (`pk_test_`, `sk_test_`), the Clerk SDK collects telemetry and prints a three-line plain-text notice on stdout once per process, among the JSON log lines. Set `CLERK_TELEMETRY_DISABLED=1` on every pilot host: the deployment sets it, and a separately configured host must set it too. With it the SDK sends nothing and prints no notice.

## Before the next design-partner invoice

The review fixes of PRs #71 to #79 make a design partner's discount dates price an invoice only once two people have checked them against the signed agreement (BIL-02). They need no migration and change no stored record, but after deploying them every design-partner agreement waits for a second person before its next invoice. Before issuing it, Finance:

1. Opens Go-live evidence and reads the note under each signed design-partner agreement's status (terms that other signed terms replace from their first month bill no month and carry none). Dates one person saved with an earlier build are shown as proposed by that person, awaiting confirmation; any other note names what stops the terms pricing an invoice, such as “Full-price terms are signed” not ticked or a date missing.
2. Asks a different Admin or Finance user from the one who proposed the dates to check them against the signed agreement and choose Confirm discount dates. Correcting the terms first proposes them afresh, and the confirmation then covers the corrected dates. In a sandbox every demo role is one visitor, so only a staff pilot can confirm.
3. Opens Reports > Billing. Once the next invoice can be priced, Issue invoice is available again. If issued invoices are listed as differing from the terms in effect (for example months invoiced under the earlier calendar-2027 rule), agrees each difference with the lender outside Valo Pay: an issued invoice is never changed, and the platform has no correction for its discount. Adjustment lines on later invoices for those invoices' collections, such as a re-allocation debit or a reversal credit, carry the same rate, so they belong in what Finance agrees with the lender too. Each issued invoice is compared with the terms in effect for its month now, as billing reads them, whichever terms billed it: a month takes the lender's signed terms in effect by its end (the later recorded on the same date), such as replacement terms added with Add terms or an amendment that applies from partway through the month. Ordinary terms give the full public price; design-partner terms count once their discount dates are confirmed. While the design-partner terms in effect for a month are not confirmed, its invoices are not compared and not listed; confirming their discount dates compares them. Each listed invoice names the terms it was compared with and when they took effect.

Do not save or confirm design-partner terms, or issue a design-partner lender's invoice, while old and new instances overlap during the deploy itself: an old instance prices dates that still await a second person and refuses saves of terms the new build has stamped. Wait until every instance runs the new build.

Rolling back to a build from before these fixes is not a way out for design-partner billing. That build prices every proposal made since the deploy at once, including dates still awaiting a second person, and refuses (400) every save of those terms with a misleading message, even a rename or unticking “Full-price terms are signed”: it drops the fields it does not know, then finds the stored proposal changed. After a rollback, issue no design-partner invoice on that build, and correct those terms only after a forward fix. Prefer a forward fix.

## What the owner does by hand

- Choose the deployment type (Autoscale or Reserved VM) and, for Autoscale, create the Scheduled Deployment above and set `VALOPAY_CLOSE_SCHEDULER=external` on the Autoscale deployment.
- Provide the secrets through Replit's secret manager, for the web deployment and for the Scheduled Deployment.
- Apply each release's migrations before publishing it (`docs/database-migrations.md`).
- Provision and renew pilot administrators with the operator command (`docs/pilot-workflow-release.md`).
