# Provider event and customer identities

Migration `009_record_identity_guards.sql` is required before publishing the build that declares `valopay_unique_provider_event` and `valopay_unique_customer_reference`. Apply it to every application schema, including each isolated runtime schema, as the database owner. It changes no record or permission and is not an application-startup migration. It is repeatable, and a host that applied it before the review fixes of 26 September 2026 applies it again in each runtime schema, as [below](#after-an-earlier-copy-of-009) says.

An event ID is unique within a lender, provider connection and delivery channel (`data.source`). The namespace uses a nonblank `data.providerConnection`, then `data.provider`, else an empty legacy namespace. ASCII case and surrounding ASCII spaces are ignored; other characters remain exact. The empty namespace is deliberately stable: changing a lender's configured provider cannot change historical evidence identity. A provider or connection must therefore accompany imports where several providers can reuse event IDs.

Provider identity fields are limited to 200 characters so that provider-scoped index keys stay bounded; an existing longer delivery namespace stops migration for review. Nonempty customer references are unique within each lender, on creation and update. Imports may identify a customer by its record ID or unique reference. A reference that matches several historical customers is refused, never resolved by list order.

## Preflight and deployment

1. Take and verify a backup and ensure the old application can be stopped during the change. Review lender-local duplicate customer references before deployment:

   `SELECT merchant_id, reference, count(*) FROM valopay_records WHERE kind='customers' AND reference<>'' GROUP BY merchant_id, reference HAVING count(*)>1;`

2. Review any duplicates the migration reports. When either preflight finds duplicates the migration stops before any schema change. Its error says how many groups there are (`groups to review: 3`), and its `DETAIL` line gives up to five of them, in order, and no other record data: a customer reference as lender and reference, and a provider delivery as lender, provider namespace, source and event ID, each value quoted (`('lender-b', 'sandbox rail', 'webhook', 'evt-9')`). The provider namespace is the one the guard compares: the connection, else the provider, without surrounding spaces and with ASCII letters in lower case, and `''` for the empty legacy namespace. Their grouping is exactly the provider expression in the file, plus lender, source and event ID; this query lists every group:

   `SELECT merchant_id, translate(coalesce(nullif(btrim(data->>'providerConnection'), ''), nullif(btrim(data->>'provider'), ''), ''), 'ABCDEFGHIJKLMNOPQRSTUVWXYZ', 'abcdefghijklmnopqrstuvwxyz') AS namespace, coalesce(data->>'source', '') AS source, data->>'eventId' AS event_id, count(*) FROM valopay_records WHERE kind='observations' AND data->>'eventId' IS NOT NULL GROUP BY 1, 2, 3, 4 HAVING count(*)>1;`

   Do not delete or merge records merely to make an index succeed. The data owner must reconcile original evidence, correct ambiguous customer references with an approved recorded change, and preserve their relationships.

3. Stop writers, then run with the database owner and the intended schema first on the search path:

   `psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f lib/db/migrations/009_record_identity_guards.sql`

   For an isolated schema, set `PGOPTIONS='-c search_path=<runtime_schema>'` for that invocation. The migration reaches the table on that search path and, in that table's schema, drops every valid unique index whose definition is exactly the reviewed old event guard's, whatever its name: a runtime schema's tables, copied with `LIKE ... INCLUDING ALL`, hold it under a generated name. Another definition under the old guard's name `valopay_unique_observation`, or an index with the old definition that is not valid (as a failed concurrent build leaves it, which can still refuse writes), stops the migration for review; drop such a leftover build once reviewed, then run the file again. A runtime schema's tables force row security, so run the file there with a login that bypasses it (a superuser or a role with `BYPASSRLS`): the duplicate checks read the records, and a login that row security applies to sees none of them, so a duplicate would then stop the migration only when its guard is built, with PostgreSQL's own message naming one duplicated key instead of the count and examples.

4. The transaction waits at most five seconds for locks and sixty seconds per statement. It takes a SHARE ROW EXCLUSIVE lock, which holds back record writes but not reads, performs duplicate preflight, builds/verifies both guards and removes the old overbroad event guard atomically. Dropping the old guard takes an ACCESS EXCLUSIVE lock on `valopay_records`, held until COMMIT, so for that final step reads of the table wait too, and a read already running, such as a long export, can make the drop reach the five-second limit. Sixty seconds per statement is ample at pilot scale; on a very large table the duplicate scans or an index build may need longer, and the file then stops with nothing changed. Raise the limit for that run on its `SET LOCAL statement_timeout` line, in a reviewed copy of the file, knowing that record writes wait for as long as it runs. A timeout, conflict, invalid index or unexpected same-name definition rolls back the entire migration. Resolve the reported condition and rerun at a suitable time; the file is repeatable.

5. Publish the matching application build and require `/api/readyz` schema status `ok`. Its readiness catalogue requires the new uniqueness definitions, and its log names each missing one with this file (`unique index valopay_unique_provider_event: apply lib/db/migrations/009_record_identity_guards.sql`); an older event index is insufficient. It also refuses the old event guard under any name: while one is in place readiness answers 503, and its log names the index and the schema to run this file in. Rehearse migration and repeated schema push in disposable PostgreSQL before production. The regression is `record-identity-migration.integration.test.ts`.

## After an earlier copy of 009

Copies of this file from before the review fixes of 26 September 2026 dropped the old event guard only by its name, `valopay_unique_observation`. A runtime schema whose tables were copied with `LIKE ... INCLUDING ALL` while the application schema still held that guard holds a copy of it under a generated name (such as `valopay_records_merchant_id_expr_expr1_idx`), which those runs left in place: the database there still refuses a second provider's delivery of an event ID another provider already sent, so such a delivery is not saved. A host that applied 009 then applies it again, as in step 3, in each runtime schema; running it again in an application schema is harmless. Run again, it finds the new guards in place and drops only the copy. The new build's readiness reports a copy still in place (`superseded unique index valopay_records_merchant_id_expr_expr1_idx: the earlier provider event guard, which refuses one event ID from two providers; apply lib/db/migrations/009_record_identity_guards.sql with valopay_runtime_staging_a first on the search path`) and answers 503 until it is gone, and the guard query in [database migrations](database-migrations.md) lists it before publishing. No record changes: a delivery the copy refused was not saved, and can be sent again once it is gone.

## Rollback

Application rollback needs a compatibility review: the earlier event guard wrongly treats the same event ID from different providers as one identity. Once new provider-scoped records exist, recreating that guard can fail. Preserve the new database guards and records while fixing forward or deploying a compatible older application; never discard provider evidence to force an old schema back. The two new guards impose no row deletion or reference rewriting.
